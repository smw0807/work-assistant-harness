# 4-C-17 읽기 단위 계약 비교 설계 결과

2026-11-17. [비교 설계](company-git-range-read-unit-design.md)를 작성하고 기존 Node 권한 안의 읽기 단위 검사 후보 A를 우선 구현 대상으로 정했다. 별도 OS helper 후보 B는 실행·권한·배포·IPC·정리 계약이 추가되므로 보류한다. **이는 새 계약의 설계와 test-only 검증이며 회사 준비의 한도 문제가 해결됐다는 결과가 아니다.**

## 이번 결과물과 변경 범위

- 설계 문서: 단위 종류·크기, 검사 시점, 결과 전달/정리, 위협 모델, profile/hash·요청/관찰/proof·회사 등록/DB 버전 분리, U1~U8 수용 기준과 구현 순서.
- `tests/company-readonly-git-range-unit-guard-experiment.test.ts`: 같은 합성 바이트를 기존 Files reader와 test-only 단위 reader로 읽는 비교 및 변경/실패 실험.
- 구현 계획에 이번 범위와 다음 구현 묶음을 추가했다. 이전 미커밋 경로 검사 반례와 결과 문서는 보존한다.

생산 source/budget/guard, 기존 profile/hash·수치 상한·CLI·DB·설정·의존성·lockfile은 바꾸지 않았다. 회사 원본·기존 실제 등록/질문·인증·native Codex·모델·외부 서비스 접근과 실제 회사 준비 재시도는0회다.

## 실험이 확인하는 것과 확인하지 않는 것

합성 파일4개의 합계는2592468바이트다. 각 파일을64KiB 이하 chunk로 두 pass에서 읽으며 읽기 호출 수·바이트·결과 hash와 metadata 계수를 비교한다. 후보 함수는 테스트 파일 안에만 있으며 CLI/application으로 연결되지 않는다.

실험은 기존 `CompanyGitRangeBudget`을 **자원 allocator로만 재사용**한다. snapshot에 남는 기존 profile hash를 후보 reader의 생산 계약으로 사용하지 않는다. 새 profile·guardPolicyHash·요청/관찰/byte proof·회사 준비 버전은 설계 상태다.

index 모양의 크기/이름을 가진 합성 바이트로 guard 비용을 확인할 뿐 유효 Git index/pack parser, OID/CRC, 객체 복원·작업 index/선택 코드 일치, safe-view, 전체 proof·DB 저장을 검증한 것은 아니다. 기존 Files의 초기 부재 관찰·목록 검사 등과 후보의 guard 실험 범위 차이를 구분한다. 단계별 read metadata 비용을 전체 회사 준비 성능으로 확대하지 않는다.

## 관찰값

얕은 합성 경로의 부모 성분 수D는 루트 포함10개다. 두 구현 모두2pass, 읽기84회, 예약/반환5184936바이트, 동일한 파일 hash, 관리 buffer 최고2609400바이트·열린 FD 최고4개를 확인했다. `lstatSync`·`realpathSync`·`fstatSync`·`openSync`·`readdirSync`를 독립 계수하여 budget metadata 합계와 일치했고 `readSync`의 호출·요청/반환 바이트도 일치했다. 이는 공개 JS API 호출 수이며 OS syscall 수가 아니다.

| metadata 단계 (두 pass 합계) | 기존 Files | 후보 단위 검사 |
| --- | ---: | ---: |
| 초기 관찰 | 116 | 0 |
| 파일 열기 | 352 | 352 |
| **읽기 단위** | **3696** | **688** |
| pass 최종 검사 | 472 | 176 |
| 전체 실험 | 4636 | 1216 |

**후보는 초기 부재 관찰과 일부 최종 검사 등을 아직 구현하지 않아 전체 합계의 감소를 검사 간격 변경만의 효과로 해석하면 안 된다.** 읽기 단위 단계는 두 구현의 같은 파일/chunk 범위를 비교했다. 부모 경로 수D·단위 chunk 수N에 대한 비용 모델은 현재 `N(4D+4)`, 후보 `(4D+4)+4N`과 일치한다. 한 chunk 단위에는4회가 추가되므로 모든 파일에서 비용이 줄어드는 것은 아니다.

동일 크기의 별도 fixture에 경로14단계를 추가한 실험에서는 기존 Files가 두 번째 pass 중metadata8192회에서 거부됐다(완료pass1, 읽기66회/4017328바이트). 후보는metadata2336회로2pass·84회/5184936바이트를 완료했으며 읽기 단위 단계는1136회였다. 이 비교도 guard 계층 실험이다. 부분 실행과 완료 실행의 시간·총계로 속도 배수를 계산하지 않으며, 실제 회사 준비가 같은 한도에서 성공한다고 결론내리지 않는다.

## 판정 차이

후보는 파일/FD를 매 chunk 전후 확인하고 전체 부모 경로는 단위 전후에 확인한다. 지속적인 조상 교체·symlink는 결과 반환 전에 거부했다. 앞선 단위가 이후에 바뀌는 경우도 pass 최종 검사에서 거부했다. 반면 단위 내부에서 조상 경로가 원래 디렉터리를 가리키는 symlink로 바뀌었다 복원되는 실험에서는 **후보가 통과하고 기존 방식은 거부했다.** 동일 바이트/hash나 적은 호출 수를 근거로 검증 동등성을 주장하지 않는다.

추가로 short read의 예약65536/반환65535바이트 보존과 정리, 경로 탈출의 FS 접근 전 거부, 검증한 열린 FD만의 본문 읽기, close 불확정 시 성공 처리·FD 계수 해제·재시도 금지를 확인했다. 새 테스트8개는 U2~U5의 일부 사례이며 모든 변경 시점·실패 조합이나 생산 통합 수용을 완료한 것은 아니다.

## 확정한 다음 구현 범위

A의 새 불변 guard/profile, 기존 버전 혼용 거부, 단위 reader를 **합성 환경 전용으로 구현**한다. U1~U7의 codec/source/두 pass·원본 변경·자원 실패 검증까지 완료한 뒤 새 회사 준비 연결 U8을 진행한다. 기존 회사 명령은 자동 전환하지 않는다. 실제 회사 적용은 새 관찰 의미와 적용 범위를 명시한 별도 단계이고, 기존 자료 접근 허용을 변경된 검증 방식의 채택으로 해석하지 않는다.
