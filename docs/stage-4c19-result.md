# 4-C-19 회사 전송 계약·로컬 검토 연결 결과

2026-11-19. 회사 준비 v3에서 별도 전송 계획·승인·relay-v3 어댑터·로컬 보고서로 이어지는 코드를 추가했다. 이번 검증은 독립 합성 저장소와 가짜 인증·전송 포트만 사용한다. 실제 회사 자료·인증정보·native Codex·모델·Slack·외부 공급자 호출은 `not_run`이다. 회사의 실제 전송이나 공급자 호환성이 검증되었다는 뜻이 아니다.

## 구현한 흐름

`유효한 v3 준비 → 새 회사 전송 계획 → 로컬 본문 검토 → 별도 단건 승인 → 승인 소비 → 계정 확인/전송 예약 → 근거 검증 → 로컬 보고서`

- `company-relay-plan-v1`과 별도 `company-relay.sqlite`를 사용한다. 기존 준비 승인 상태, `company-investigation-plan-v1`의 모의 승인과 개인/relay 승인을 승격하거나 재사용하지 않는다.
- `company-relay-authorization-v1`은 회사 전송 허용·제공자 조건 확인·계정 ID의 SHA-256·relay-v3 설정을 담는 운영자 선언이다. 기본 예시는 비활성·미확인이고, 선언과 relay 설정 모두 활성화되어야 계획을 만들 수 있다. 이 선언은 독립적인 회사 정책 검증이나 특정 요청의 단건 승인이 아니다.
- 계획은 준비 계획·runtime·원본/안전 근거의 결합과 정확한 입력·요청 본문·HTTP 명세·연결 profile·설정·선언·계정 hash를 고정한다. 회사 입력은 `company-relay-input-v1`이며 개인 또는 합성 저장소 입력으로 변환하지 않는다.
- 전송 대상은 기존 ChatGPT relay endpoint, 모델은 `gpt-6.1-sol`, 인증은 `chatgpt`다. 요청은 `tools:[]`, `store:false`, `stream:true`, redirect 거부와 재시도 0을 유지한다. 대상 코드 실행과 수정 권한은 없다.
- 계획·승인·호출 전, 인증 접근 직전, 전송 직전과 완료 후에 준비와 source를 확인한다. source 검증은 기존 회사 v3의 두 pass와 한도를 사용한다. native 경로가 대상 저장소 안에 있는 경우도 거부한다.
- 승인 소비와 전송 예약은 각각 SQLite 트랜잭션으로 먼저 확정한다. 전송 직전 callback이 성공하기 전에는 가짜/실제 upstream에 요청을 보내지 않는다. 같은 준비·계정·설정의 재계획도 기존 기록을 반환하며 소비한 승인을 되살리지 않는다.
- 실제 어댑터는 승인 소비 이후에 구성한다. 기존 relay broker가 인증 구조를 검증한 다음 계정 ID hash를 비교하며, 다른 계정이면 전송 예약과 upstream 호출 전에 거부한다. 토큰이나 원래 계정 ID는 계획·검토 자료·보고서에 저장하지 않는다.
- 취소·만료 이후 늦은 결과를 보고서로 채택하지 않는다. 정리 불확정은 `BLOCKED`로 남기고 재호출하지 않는다. 복구 명령은 상태를 보수적으로 닫으며 인증 접근·전송·프로세스 종료 성공을 만들어 내지 않는다.

설정 파일은 각 명령 시작 시 읽고 계획의 선언과 비교한다. 진행 중인 실행은 그 선언의 메모리 snapshot을 사용하므로 JSON 수정 자체가 즉시 취소를 뜻하지 않는다. 활성 실행을 중지하려면 같은 작업에 `company-relay-cancel`을 사용한다. 이미 전송한 자료의 회수나 공급자 측 처리 중단은 보장하지 않는다.

## 로컬 검토와 보고서

`company-relay-review`는 private runtime의 `reviews/<task-id>.json`에 검토 자료를 만든다. 계획·모델·목적지·계정 hash·예산·기한과 정확한 요청 명세 및 검증한 보고서를 함께 보여 준다. `requestEnvelope.body` 문자열이 실제 승인 대상 전송 바이트이며, JSON 파일 전체의 표시용 들여쓰기는 전송 형식이 아니다.

검토 자료에는 준비 payload의 로컬 source root·파일 identity·원시 인증·raw relay 응답을 복사하지 않는다. 디렉터리는 `0700`, 파일은 `0600`이며 symlink·hardlink·다른 소유자·공개 권한을 거부한다. 검토 파일은 승인 원장이 아닌 재생성 가능한 사본이고 `fsync`에 의한 전원 장애 내구성을 주장하지 않는다. 기존 검토 자료를 임의 위치로 export하는 기능은 제공하지 않는다. 사용자가 별도로 복사한 파일은 관리 대상이 아니므로 그 사본의 보관은 사용자가 처리해야 한다.

stdout에는 상태·식별자·hash·기한·승인/시도/전송 예약 수와 보고서·검토 자료 존재 여부, 정리 계수를 출력한다. `prunedArtifactRuns`·`prunedArtifactManifests`는 제거한 native 감사 metadata를, `preservedUncertainArtifacts`는 불확정으로 보존한 항목을 나타낸다. 질문·코드·답변 본문과 원시 오류는 출력하지 않는다. `runStatus:succeeded`는 명령 완료를 의미한다. 유효한 조사 보고서는 `status:REPORTED`, 소비된 승인, 시도/예약 각 1회와 보고서 존재를 함께 확인한다. 예약 횟수는 실제 공급자 호출 횟수의 독립적인 증거가 아니다. 결과 유실은 `unknown`으로 표시하며 같은 ID를 조회하고 자동 재시도하지 않는다.

응답에는 기존 strict JSON·민감정보·선택된 근거 ID/줄 범위 검증을 적용한다. 새 보고서의 `resultHash`는 검증된 결과의 canonical JSON hash, `finalTextHash`는 최종 텍스트 hash, `responseHash`는 relay 응답 hash다. 원시 응답은 보관하지 않는다. 가짜 포트의 보고서는 실제 모델·native·인증 접근·외부 전송을 모두 `not_run`으로 표시한다. 보고서 의미 정확성과 기존 relay의 공급자 metadata/sequence/tool 사용 검사 한계는 그대로 남는다.

## 보관과 정리

본문·보고서·관리되는 검토 사본은 최초 준비의 `expiresAt`, 감사 metadata는 `auditExpiresAt`을 상속한다. 새 계획이나 승인으로 기한을 늘리지 않는다. 승인 TTL은 1~60분 범위에서 원래 본문 기한으로 제한한다. 준비 취소는 후속 작업을 차단하지만 이미 만들어진 별도 전송 DB와 검토 파일의 즉시 연쇄 삭제를 뜻하지 않는다. 즉시 제거하려면 해당 전송 작업도 취소한다.

정리는 CLI 명령을 실행할 때 수행한다. 백그라운드 예약 삭제나 파일시스템·백업의 물리적 완전 삭제를 보장하지 않는다. 원래 기한이 지나면 DB 본문과 관리되는 검토 사본을 제거한다.

native 경로에는 원래 감사 기한과 계획/전송 hash를 결합한 별도 retention metadata를 먼저 기록한다. 감사 기한 후 lifecycle·child 종료·scratch 부재가 확인된 실행의 고정 metadata만 제거한다. 격리 진단의 `host-canary.txt`는 private 파일 권한·identity·고정 합성 내용이 일치할 때만 제거 대상에 포함한다. 알 수 없는 파일이나 다른 내용은 재귀 삭제하지 않는다.

중단된 기록, 남은 scratch, 종료 불확정 또는 결합을 확인할 수 없는 native 디렉터리는 감사 기한이 지나도 자동 제거하지 않는 예외다. 안전한 종료와 잔여 자료 처리는 운영자가 확인해야 한다. 이 경우 `recover`가 실제 프로세스 정리를 완료했다고 주장하지 않는다. 짧은 IPC 디렉터리는 worker가 시작되지 않았거나 종료가 확인된 경우에만 정리를 시도한다. 소유 identity와 비어 있음을 확인한 디렉터리만 제거하며, 종료·정리 불확정은 보존하고 성공으로 보고하지 않는다.

## 실행 환경과 기존 계약

Nest application context의 worker를 사용한다. 준비 DB 사전검사는 네트워크·하위 프로세스 없는 Node 권한 child에서 수행하고, 선언이 비활성/미확인 상태이면 준비 DB를 열기 전에 거부한다. 새 runtime을 만들기 전에 대상·하네스·준비/runtime 중첩을 검사한다.

모든 worker는 최소 LANG/TZ 환경과 V8 old-space 128MiB, 고정된 하네스 진입점을 사용한다. 사전검사와 `run` 이외의 명령은 Node 권한 모드를 유지한다. 쓰기는 고정된 전송 store·reviews·native metadata 디렉터리와 필요한 기존 준비 store로 제한하며 네트워크·child·추가 worker·addon·WASI·inspector를 허용하지 않는다.

설치된 Node 26에서 합성 검증한 결과, Node 권한 모드는 허용된 파일에도 `fsync`를 차단해 `writeFile`의 `flush:true`와 기존 native lifecycle 기록을 수행할 수 없었다. 재생성 가능한 검토 사본에서는 flush를 사용하지 않고, 내구성이 필요한 기존 승인/실행 기록의 동작은 약화하지 않았다. 명시적인 `company-relay-run`의 controller만 기존 readonly relay와 동일한 신뢰 경계로 분리해 Node 권한 모드 없이 실행한다.

따라서 `run` controller에는 실행 사용자의 주변 OS 권한이 있으며 네트워크·하위 프로세스·파일 접근을 Node 권한 모드로 격리했다고 주장하지 않는다. 신뢰하는 하네스 코드가 고정 경로·명령·목적지와 전송 전 승인·계정·source 검사를 수행한다. 이 구분은 일반 명령의 권한 격리를 실제 전송 controller의 보증으로 확대하지 않기 위한 것이다. 실제 모델 child는 기존 relay의 macOS SBPL·로컬 broker·guardian 경로를 그대로 재사용하며, 이 단계에서 그 native 경계를 실행 검증하지 않았다.

짧은 IPC 디렉터리는 준비와 경로 중첩 사전검사를 통과한 뒤 부모가 새로 할당한다. 실제 IPC 경로도 worker에서 다시 검사한다. 신뢰하는 `run` controller가 사용할 IPC 경로를 하나로 고정한 것이며, controller 전체에 `/private/tmp` 쓰기 권한이 없다는 뜻은 아니다. 모든 source 읽기 범위는 하네스 코드로 제한하며 OS 전체 읽기 격리가 아니다. V8 old-space 한도는 프로세스 RSS 강제 상한이 아니고, CLI supervisor는 부모 생존과 OS 신호 처리에 의존한다.

전체 CLI 기한은 사전검사를 포함해 `run` 125초, 나머지 30초다. 사전검사는 출력 8KiB와 강제 종료를 적용한다. run supervisor는 명령 시작 120초에 SIGTERM을 요청하고 남은 총125초 안에서 최대5초의 정리를 기다린다. 출력 초과도 남은 시간과5초 중 작은 유예를 적용한다. 비실행 명령은30초 뒤 SIGTERM과250ms 유예를 유지하며, 모두 close 확인 전 성공 처리하지 않는다. 이 전체 기한 때문에 오래 걸리는 사전검사·source 재검증은 모델 호출에 남는 시간을 줄일 수 있다.

기존 relay-v3의 작업 120초·공유 정리 5초·총 125초, 응답 4MiB·frame 64KiB/8192개·JSON 깊이 16·최종 출력 16KiB·native 출력 128KiB·stderr 16KiB를 유지한다. 입력 128KiB·요청 256KiB와 기존 회사 판독/수집 한도도 변경하지 않았다. 구형 relay·개인·회사 모의 계약과 hash를 새 계약으로 바꾸지 않는다. 공통 어댑터에는 별도 회사 정책의 계정 검사와 전용 IPC 경로만 추가한다.

패키지 매니저는 설치된 현재 pnpm을 사용한다. 버전 고정·설치·다운로드·패키지 매니저 변경과 의존성/lockfile 변경은 이번 범위에 포함하지 않는다.

## 검증

현재 설치된 pnpm 12.16.1과 Node 26.12.1로 최소 환경에서 검사했다. 설치·다운로드·버전 고정은 하지 않았다.

| 검사 | 결과 |
| --- | --- |
| lint / typecheck | passed |
| build | passed — 전체 회귀에서도 재컴파일 |
| 회사 신규 합성 검사 | passed — 92개, 전체 회귀에 포함. 수정 후 CLI·산출물·supervisor 집중 33개도 통과 |
| 전체 회귀 | passed — 총1886개, 통과1850개·실패0개·native opt-in 미실행36개 |
| 기존 계약·한도·lockfile 보존 | passed — HEAD 기준532개 중 의도한8개만 수정, 나머지524개 동일. 구형 순수 정책·기존 수치·package/lockfile 보존 |
| 실제 회사 자료·인증·native·모델·Slack·외부 공급자 호출 | not_run — 이번 범위에서 제외 |

초기 회사 검사에서 로컬 검토 사본의 fsync 실패를 확인해 수정했다. 가짜 broker의 loopback 소켓이 제한 환경에서 차단되어 승인된 동일 최소 환경에서 다시 검사했다. 최종 전체 회귀는 이 두 문제를 해결한 코드로 통과했다. 전체 검사 중 실제 공급자·인증·native opt-in은 실행하지 않았다.

합성 검사는 비활성/미확인 선언, 구형 모의 승인 혼용, 계획·계정·설정·본문·예산 변조, 제공하지 않은 근거, 중복 JSON 키, source 변경, 동시 소비와 중복 전송 거부, 취소·만료·늦은 응답·복구를 다룬다. private DB/파일 권한과 링크, 원래 기한의 본문·보고서·검토 사본 정리, 종료된 native metadata의 제한된 삭제와 불확정 자료 보존도 검사한다. CLI 출력에는 본문을 내보내지 않고, 주변 환경의 인증 canary가 worker 환경에 들어가지 않는지 확인한다.

계정 불일치 전송 거부는 가짜 인증과 가짜 upstream을 사용하는 loopback broker로 검사한다. 이러한 검사는 실제 인증 접근이나 native Codex를 실행한 것이 아니며 실제 공급자 전송 성공 근거로 사용하지 않는다.

## 다음 최소 작업

미확인인 회사의 제공자·모델/계정·전송 가능 자료 조건만 확인하고, 실제 인증·native·단건 모델 호출을 제외한 현재 범위를 해제하는 명시적인 승인을 받아야 한다. 이미 확인한 회사 반입·읽기/보관 조건을 다시 질문하지 않는다. 별도 회사 보관 기한이 없다는 기존 답변도 유지하고, 현재 앱의 보관 기한을 임의로 늘리지 않는다.

그 뒤 유효한 새 준비를 만들고 정확한 본문·목적지·계정 hash·한도·기한을 로컬에서 검토한 다음 해당 계획 hash에 대해서만 새 단건 승인을 받는다. 승인된 한 번의 실제 호출과 보고서 검토가 다음 검증 범위다. 과거 모의 성공, 이번 가짜 전송 성공 또는 다른 계정의 기존 승인을 실제 회사 호출 승인으로 사용하지 않는다. Slack 자동 응답·대상 코드 수정·대상 테스트/빌드·push·배포는 이 작업에 포함하지 않는다.

검사 로그·최종 집계·HEAD/현재 파일 hash와 보존 감사는 소유자 전용 로컬 위치 `/private/tmp/harness-company-relay-tb0fdhor`에 보관했다. 이 문서에는 회사 질문·코드·실제 인증정보를 포함하지 않는다. 커밋·외부 게시·push는 수행하지 않았다.
