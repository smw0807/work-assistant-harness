## 1. 신뢰 경계

- **소유자:** 로컬 CLI에서 표시된 계획을 검토하고 실행을 승인하는 사람.
- **요청자:** Slack에서 문의나 변경 요청을 보낸 사람. 요청은 조사 대상이며 소유자의 실행 승인이 아니다.
- **모델:** 분류·설명·계획을 제안한다. 권한을 만들거나 변경하지 못한다.
- **외부 자료:** Slack 본문, 저장소 파일, README, 코드 주석과 도구 출력. 그 안의 명령문은 신뢰할 실행 지시가 아니다.
- **정책과 실행 환경:** 실제 접근, 명령과 전송 여부를 강제한다. 모델 출력은 이 경계를 우회할 수 없다.

MVP의 승인 경로는 로컬 CLI뿐이다. 현재 OS 사용자와 승인 저장소의 파일 권한이 신뢰 경계다. 같은 OS 계정을 공유하거나 호스트가 침해되면 이 가정이 깨질 수 있으므로 다중 사용자 원격 승인 서비스와 동등한 인증을 제공한다고 주장하지 않는다.

단계 3-A의 소유자 ID는 `process.getuid()`가 반환한 `os-user:<uid>`로 고정한다. CLI 옵션이나 Slack ID로 소유자를 지정하지 않는다. UID가 지원되지 않으면 승인·취소를 거부한다. 승인·취소는 기존 전역 lease를 요구하므로 같은 데이터 디렉터리의 실시간 Slack 수신 중에는 수행하지 않는다. 이 제한은 오프라인 승인 기능의 한계이며 수신 중단 동안의 요청 변경 감지를 보장하지 않는다.

## 2. 행위별 승인

| 행위 | 조건과 경계 |
| --- | --- |
| 하네스 자체의 개발·검증 | 요청된 개발 범위에서 진행한다. 대상 제품 저장소의 수정 권한으로 확대하지 않는다. |
| 대상 코드 읽기·초안 작성 | 사전 허용된 저장소·커밋·경로와 데이터 처리 범위 안에서만 한다. 대상 파일 수정이나 스크립트 실행은 포함하지 않는다. |
| 대상 코드 변경·검사 실행 | 단계 3 이후, 구체적인 계획에 대한 유효한 소유자 승인을 **실제 변경이나 실행 전에** 확인한다. |
| 의존성 설치·테스트 설정 변경 | 실행 코드와 외부 연결을 수반할 수 있으므로 계획에 별도로 명시한다. 코드 수정 승인에 묵시적으로 포함하지 않는다. |
| 요청자 답장·소유자 Slack DM | 수신자·채널·전송 내용 또는 명확한 내용 범위를 별도로 허용받는다. 4-A는 가짜 어댑터만 사용한다. 4-B-2는 기본 비활성이며 승인된 개인 테스트 스레드의 고정 합성 문구를 새 live 승인 후 한 번 게시하는 경로만 제공한다. DM·실제 업무 답장은 연결하지 않는다. 로컬 보고서 생성이나 코드 변경 승인은 전송 승인이 아니다. |
| Git push | 초기 범위 밖이다. 원격·브랜치·커밋·대상 diff를 별도로 승인받는다. 로컬 변경 승인을 재사용하지 않는다. |
| PR/MR 생성 | 하네스가 Codex에 지시하는 대상 저장소 작업과 후속 구현 범위에서 제외한다. |
| 병합·배포 | 첫 버전에서 구현하지 않는다. 후속 도입 시 독립된 승인과 운영 정책을 정한다. |
| 회사 자료를 외부 AI로 전송 | 회사가 허용한 제공자·실행 위치·자료 범위·보관 조건이 먼저 충족되어야 한다. 개인의 수정 승인이 회사의 데이터 반출 승인을 대신하지 않는다. |

권한이 불명확하거나 정책 검증이 실패하면 해당 동작을 차단한다. 정책 오류를 기본 허용으로 바꾸거나 다른 도구로 우회하지 않는다.

## 3. 승인 전 보여 줄 계획

소유자가 무엇을 허용하는지 확인할 수 있도록 다음 내용을 함께 표시한다.

- 작업 ID, 대상 저장소 ID와 기준 커밋.
- 원래 요청과 메시지 revision, 목적과 기대 동작.
- 수정할 파일 또는 좁은 경로 범위와 허용할 변경.
- 실행할 등록 명령 ID와 인자, 설치·외부 연결 필요 여부.
- 예상 위험, 한계와 검사 계획.
- 계획 버전과 해시, 승인 만료 시각과 취소 방법.

승인 유효기간은 설정값이다. 계획서의 30분은 예시이며 확정된 운영 정책으로 하드코딩하지 않는다.

단계 3-A CLI에서는 `--expires-in-minutes`를 필수로 받고 1~1440분의 정수만 허용한다. 이 입력 범위는 로컬 승인 기록의 한도이며 회사 운영 정책의 승인 근거가 아니다.

### 승인 기록과 소비

승인은 `ownerId`, `taskId`, `planHash`, `baseCommit`, 허용 동작, 만료 시각, 취소·사용 상태에 묶는다. `planHash` 계산에는 대상 저장소, 요청 revision, 허용 파일·명령 등 승인 대상 내용을 포함한다.

- 작업 ID만 일치하거나 모델이 실행을 권했다고 승인하지 않는다.
- 계획 내용, 저장소, 기준 커밋 또는 요청 revision이 바뀌면 기존 승인을 무효화한다.
- 실제 실행 직전에 기준 커밋과 모든 승인 조건을 재검증한다.
- 승인 소비와 `RUNNING` 전환은 원자적으로 처리한다. 동일 승인으로 중복 실행하지 않는다.
- 새 파일, 더 넓은 변경, 새 명령·인자 또는 다른 외부 연결이 필요하면 멈추고 새 계획을 제시한다.
- 중단된 실행의 결과가 불확실하면 상태와 작업물을 먼저 조사한다. 재시작 자체를 재실행 승인으로 취급하지 않는다.

단계 3-A는 아래 범위로 제한한다.

- 승인 불변 스냅샷에는 계획·해시·요청 revision·저장소·기준 커밋을 고정하고 별도 SQLite 테이블에 보존한다. 승인 생성과 `APPROVED` 전환은 같은 트랜잭션이며 활성 승인을 중복 생성하지 않는다.
- 만료 조정은 승인 취소와 `AWAITING_APPROVAL` 복귀를 함께 기록한다. 로컬 취소는 승인 대기·승인됨 변경 요청만 `CANCELLED`로 바꾼다. 요청 편집·삭제도 Task 무효화와 같은 트랜잭션에서 기존 승인을 취소한다. Task 계획·보고를 제거해도 불변 승인 스냅샷은 유지한다.
- `executionPolicy`는 `approval-only-v1`이며 `usedAt`은 `null`이다. 승인 소비·Run 생성·대상 수정과 검사는 구현하지 않는다. 후속 실제 실행 정책의 새 승인을 요구하며 이 기록을 재사용하지 않는다. `ExecutionPort`는 항상 거부하고 `run` 명령은 없다.
- 이 경로의 기준 커밋 검증은 Task·계획·CLI 입력의 일치 검사다. 별도 3-C 합성 실행의 새 승인과 혼용하지 않는다.

## 4. 읽기 전용은 권한으로 강제한다

“수정하지 말라”는 프롬프트와 실행 후 diff 검사만으로는 부족하다. 다음 제한을 구현하고 검증한다.

1. **대상 입력 고정:** 허용된 저장소와 기준 커밋의 스냅샷을 읽는다. 소유자의 기존 작업 디렉터리를 조사 중에 갱신·checkout·reset하지 않는다.
2. **도구 분리:** 조사 경로에는 읽기용 포트만 제공한다. 파일 쓰기, 임의 쉘, 패키지 실행과 Git 원격 도구는 제공하지 않는다. 기본 `ExecutionPort`는 항상 거부한다.
3. **쓰기 권한 분리:** 대상 소스는 읽기 전용 마운트나 동등한 파일시스템 권한으로 보호하고, 보고서·SQLite를 위한 쓰기 경로는 따로 둔다. 정책 검사가 실패했을 때도 대상 쓰기가 가능하지 않은지 검증한다.
4. **경로 검증:** 저장소 root와 실제 경로를 정규화하고 symlink, `..`, 절대 경로 등을 통한 root 밖 접근을 차단한다. 읽기 시점에도 허용 경로 안에 있음을 확인한다.
5. **자료 제한:** 허용 목록과 제외 규칙을 함께 적용한다. 비밀 파일, 개인 키와 자격증명, 불필요한 개인정보, 바이너리와 과도하게 큰 파일을 제외한다. 필요한 줄만 모델 입력에 넣는다.
6. **결과 검증:** 조회 전후 파일 해시와 상태를 비교한다. Git diff만으로 누락될 수 있는 새 파일과 추적되지 않은 파일도 고려한다. 이것은 방어 장치의 검증이지 쓰기 차단의 대체물이 아니다.

대상 저장소의 `package.json`에 있는 test·build·install도 임의 코드를 실행할 수 있다. 조사 단계에서는 실행하지 않는다. Git을 사용할 때도 필요한 읽기 동작만 제공하고 hooks나 외부 명령 실행 경로를 열지 않는다.

하네스 테스트를 위해 합성 저장소를 임시 경로에 준비하는 행위와 실제 조사 중 대상을 바꾸는 행위를 분리한다. “테스트용”이라는 이유로 회사 저장소나 소유자의 기존 변경을 사용하지 않는다.

## 5. 승인 후 실행의 격리

별도 브랜치와 worktree는 원래 작업 디렉터리와 변경을 분리하는 수단이다. **worktree는 보안 sandbox가 아니다.** Git 메타데이터를 공유하며 같은 OS 권한으로 다른 파일이나 네트워크에 접근할 수 있다.

후속 Codex 실행 연결에서는 하네스가 대상 저장소의 작업 유형·브랜치 이름·기준 커밋을 계획과 승인에 묶는다. 유효한 승인과 격리 환경을 확인한 뒤 `feature/`, `fix/`, `chore/`, `refactor/` 등 작업 성격에 맞는 브랜치를 만들고 그 안에서만 수정한다. 기준 브랜치와 기존 사용자 작업을 보존하며, 브랜치 충돌을 덮어쓰기나 reset으로 해결하지 않는다. PR/MR 생성은 지시하거나 실행하지 않으며 commit·push 승인은 코드 수정 승인에서 분리한다. 이 규칙은 대상 저장소의 실제 연결에 대한 후속 설계로 현재 하네스 저장소의 개발 규칙을 뜻하지 않는다. 4-C-1의 오프라인 모의 계약과 실제 브랜치 작업 권한은 구분한다. 상세 범위는 [4-C 계획](implementation-plan.md#후속-단계의-별도-범위)을 따른다.

실행 기능을 열기 전에 다음을 검증한다.

- 쓰기 가능한 경로를 승인된 작업 영역으로 제한하고, 원래 작업 디렉터리와 승인 저장소를 보호한다.
- 실행 프로세스에 개인·회사 자격증명, SSH 키, 클라우드 토큰 등 호스트의 비밀을 상속하지 않는다.
- 네트워크는 기본 차단한다. 필요한 연결은 계획과 정책에 목적지·용도를 좁혀 명시한다.
- 명령은 사전에 등록한 `commandId`와 인자 스키마로 선택한다. 모델이 만든 문자열을 셸 명령으로 실행하지 않는다.
- 인자, 실행 파일과 작업 디렉터리를 검증한다. 등록된 테스트도 저장소 코드를 실행하므로 격리 제한을 유지한다.
- 실행 시간, 메모리와 출력 크기를 제한하고 취소 시 하위 프로세스도 종료할 수 있게 한다.
- 승인된 파일 범위와 실제 diff를 비교한다. 승인되지 않은 변경, 외부 전송 시도 또는 검사 실패를 성공으로 표시하지 않는다.

기본 결과는 로컬 diff와 검사 보고다. 자동 commit, 자동 push, worktree의 자동 삭제와 실패 작업물의 자동 정리는 하지 않는다. 의도치 않은 변경을 발견해도 기존 사용자 작업을 지우는 방식으로 복구하지 않는다.

위 실행 격리는 단계 3-B 이후의 요구사항이다. 지원할 backend와 버전, 준비·검증 실패 시 거부 조건을 정하고 호스트 파일·원본·승인 DB·공유 Git 메타데이터·외부 통신 차단을 실제 환경에서 실증한 뒤 실행 기능을 연다. 단계 3-C는 고정 합성 patch부터 시작하고 명령의 실행 파일·argv·cwd·환경·네트워크·자원 한도와 정책 버전을 승인 계획에 묶는다. 단계 3-D는 실시간 수신과 실행 잠금·요청 무효화 경합, 프로세스 트리 취소와 crash 복구를 검증한다. 상세 순서와 수용 기준은 [단계 3 계획](implementation-plan.md#단계-3-승인-후-코드-변경)을 따른다.

### 단계 3-B의 합성 Docker 진단

`sandbox-check`는 고정 합성 probe를 검증하는 전용 경로다. 초기 지원은 macOS `darwin/arm64`와 Docker Desktop의 Linux `aarch64` daemon, cgroup v2, 기본 seccomp다. 명시한 로컬 Unix socket과 정확한 Engine·이미지·Node·`docker-probe-v1` 정책 identity를 검사한다. 비활성 설정에서는 Docker에 접속하지 않는다. 지원 밖 환경, 준비 실패, 유효 정책 불일치와 정지·제거 미확인은 차단 또는 실패로 기록한다. 로컬 이미지가 없을 때 자동으로 다운로드하거나 다른 backend에서 재시도하지 않는다.

진단 controller는 신뢰하는 하네스 코드이며 `/usr/local/bin/docker`를 shell 없이 고정 argv로 호출한다. 새로운 `0700` Docker 설정 디렉터리가 비었는지 확인하고 명시적인 socket, 최소 환경변수를 사용한다. 기본 사용자 Docker 설정에는 인증된 proxy 주소가 포함될 수 있고 새 container에 자동 주입되므로 읽지 않는다. 이미지의 환경변수와 `VOLUME`도 검사하고, 고정 entrypoint와 비활성 healthcheck로 이미지 기본 동작을 제한한다. [Docker CLI proxy 설정](https://docs.docker.com/engine/cli/proxy/), [Dockerfile의 ENV·VOLUME](https://docs.docker.com/reference/dockerfile/)

container 정책은 nonroot UID/GID `1000:1000`, 읽기 전용 root, 모든 capability 제거, 권한 상승 금지, private cgroup·IPC, 기본 seccomp다. `--network none`으로 loopback만 두고 TCP·DNS 실패를 함께 확인한다. workspace 한 곳만 bind mount하며 원본·하네스·승인 DB·공유 Git·홈·Docker socket은 마운트하지 않는다. `--ipc none`으로 `/dev/shm`의 추가 쓰기 영역을 없애고 daemon의 외부 log driver를 사용하지 않는다. [Docker 실행 옵션](https://docs.docker.com/reference/cli/docker/container/run/), [none 네트워크](https://docs.docker.com/engine/network/drivers/none/), [기본 seccomp](https://docs.docker.com/engine/security/seccomp/)

합성 보호 파일의 절대경로·경로 탈출·symlink·`/proc/1/root` 접근 실패와 전후 hash 동일 여부를 확인한다. 쓰기가 허용된 workspace의 positive control도 필요하다. 호스트의 실제 비밀이나 승인 DB를 검사 자료로 사용하지 않는다. Docker Desktop의 bind mount는 Linux VM을 통해 macOS 경로를 공유하므로 VM을 쓴다는 사실만으로 호스트 경로가 보호된다고 간주하지 않는다. [Docker bind mount 경계](https://docs.docker.com/engine/storage/bind-mounts/)

고정 한도는 메모리 128MiB·swap 0·PID 64개·CPU 0.5개, 시간 probe 1.5초, stdout/stderr 합계 16KiB다. cgroup 값과 실제 PID 생성 거부·OOM을 확인한다. CPU는 quota 값 검증이며 성능 보장은 아니다. 시간·출력 초과 때는 Docker CLI 종료와 별개로 이 진단이 생성한 container를 소유권 확인 후 강제 종료하고, 정지 상태와 제거를 확인한다. detached child의 시작 파일·종료 코드 137·OOM 아님을 확인하고 지연 marker가 남지 않아야 한다. 고정 합성 probe의 7.5초 watchdog은 보조 종료 장치다. 생성 RPC가 불확실하게 끝난 뒤 현재 부재만 확인한 경우에는 정리 완료로 인정하지 않는다. container 이름과 정리 미확인 결과, 합성 작업물과 보고서를 검토용으로 보존한다. [Docker 자원 한도](https://docs.docker.com/engine/containers/resource_constraints/), [container 종료](https://docs.docker.com/reference/cli/docker/container/kill/)

진단 결과의 `executionEnabled`는 항상 `false`다. 보고서를 승인·실행 권한으로 사용하지 않고 `approval-only-v1` 승인도 소비하지 않는다. 읽기 worker의 네트워크·하위 프로세스 차단은 유지한다. 단계 3-C는 아래 별도 합성 실행 흐름을 사용하며 실행 중 요청 변경·취소·crash 복구는 3-D 범위다.

신뢰 경계에는 Docker daemon과 Desktop VM·Linux 커널이 포함된다. 이 검증은 알려진 제한과 canary 결과이며 container escape의 완전한 방지나 회사 도입 승인을 보장하지 않는다. 고정 공식 이미지의 초기 다운로드는 backend 준비이며 회사 자료나 토큰을 전달하지 않는다. 실제 회사 자료·네트워크·비밀 주입은 이번 진단에 포함하지 않는다.

### 단계 3-C의 고정 합성 실행

`execution-plan`·`execution-approve`·`execution-run`·`execution-inspect`는 기존 조사와 별도의 합성 전용 경로다. CLI에 저장소 경로·patch 본문·shell·임의 argv 입력을 제공하지 않는다. 고정 fixture만 사용하며 실제 AI와 Slack 요청을 실행으로 연결하지 않는다. 원본·실행 계획·승인·Run은 `execution.sqlite`와 비공개 `executions/`에 보관하고 기존 `tasks.sqlite`의 `approval-only-v1`은 조회하거나 소비하지 않는다.

`synthetic-execution-v1`의 계획 해시에 다음을 고정한다.

- task ID·고정 요청 revision·합성 repo ID·기준 커밋·원본 전체 해시.
- 수정 허용 파일 `src/message.mjs`, 기존 일반 파일 내용 교체의 전후 해시와 고정 내용. 파일 생성·삭제·이름 변경·실행 비트·symlink·서브모듈은 거부한다. 읽기 근거는 수정 허용 범위가 아니다.
- 명령 ID·실행 파일 `/usr/local/bin/node`·정확한 argv·인자 없음·cwd `/workspace`·고정 최소 환경·네트워크 없음·시간·자원 한도.
- 정확한 Engine·Node·로컬 이미지 ID, 실행 정책 버전과 `enabled`·socket을 포함한 설정 해시. 설정 변경은 새 계획과 승인을 요구한다.

승인은 현재 OS UID의 `os-user:<uid>`로 고정하고 TTL 1~1440분을 검증한다. 계획과 승인은 Docker에 접속하지 않는다. 실행 직전 원본 일반 파일·Git 객체·메타데이터·커밋·전체 해시, 계획·승인 snapshot·요청 revision·정책과 backend identity를 다시 검증한다. 실행 준비 중 흐른 시간도 TTL에 반영한다. 승인 소비·Run 삽입·`RUNNING` 전환을 `BEGIN IMMEDIATE` 한 트랜잭션에서 처리하고 소비 실패·저장 실패는 전부 rollback한다. task당 Run 하나와 승인당 소비 한 번을 DB 제약으로 제한한다. 실패·완료·controller 강제 종료 뒤에도 소비를 되돌리거나 자동 재실행하지 않는다.

합성 원본은 동결하고 독립 Git 저장소의 작업 트리를 고정 파일에서 재생성한다. 원본 `.git`을 공유하지 않는다. 승인 patch를 적용한 뒤 실제 변경 경로·내용·권한·Git 메타데이터를 확인하고 container에는 Git 없는 읽기 전용 view만 마운트한다. 원본·승인 DB·하네스·호스트 홈·socket·Git 메타데이터는 마운트하지 않는다. 호스트에서 합성 검사 파일을 import하거나 실행하지 않는다.

container는 3-B와 같은 nonroot·읽기 전용 root·네트워크 없음·capability 제거·권한 상승 금지·기본 seccomp 경계를 유지한다. 쓰기 영역은 `/tmp`의 `rw,noexec,nosuid,nodev,size=16777216` tmpfs 하나로 제한하며 별도의 `/dev/shm`을 허용하지 않는다. 메모리 128MiB·swap 0·PID 64·CPU 0.5개·시간 3초·stdout/stderr 합계 16KiB를 강제한다. 실행 view는 파일 수 16·전체 64KiB 한도를 가진다. 생성 후 시작 전 inspect에서 정확한 command·mount·tmpfs·환경·한도·권한을 대조하고 예상 밖 mount·쓰기 영역을 거부한다.

시간·출력 초과나 정상 신호 취소 때 controller는 자기 container만 소유권을 확인해 kill하고 정지·제거 결과를 남긴다. 생성 응답이 불확실하면 단순 부재만으로 정리 성공을 주장하지 않는다. 출력 한도는 수신 chunk에서 감지하므로 관찰 바이트 수가 임계값보다 클 수 있다. 원시 stdout/stderr나 Docker 오류를 저장하지 않고 관찰 바이트 수·출력 해시·고정 오류 코드만 보관한다. 실제 diff는 합성 파일 내용과 전후 해시를 포함하며 원본 전체 전후 해시와 검사별 `passed`·`failed`·`not_run`을 기록한다.

계획·승인·실행·복구는 전역 lease를 유지해 실제 Slack 수신과 직렬화한다. 아래 합성 제어·조회만 짧은 실행 DB 트랜잭션을 사용한다. Docker daemon·Desktop VM·Linux 커널과 같은 OS 사용자는 계속 신뢰 경계에 포함되며 범용 악성 코드나 실제 회사 자료의 실행 검증을 완료했다고 주장하지 않는다.

### 단계 3-D의 합성 제어·중단 복구

`execution-cancel`·`execution-invalidate`는 OS UID 소유자를 확인하고 합성 요청 `synthetic:<task-id>`의 revision·generation을 갱신한다. 초기 revision은 1이며 편집·삭제는 현재보다 큰 정수 revision(최대 1000000000)만 적용한다. 같은 이벤트 ID·내용은 멱등 처리하고 다른 내용의 ID 재사용은 거부한다. 오래된 이벤트는 기록만 남긴다. 대기 Task의 취소와 미소비 승인 revoke는 제어 기록과 한 트랜잭션이며, 실행 중 제어는 Run을 즉시 완료 처리하지 않는다. 승인 생성·소비와 최종 Run 종료가 같은 트랜잭션에서 요청 fence를 확인한다. 취소된 실행의 정리가 확인되지 않으면 `CANCELLED`로 단정하지 않고 `BLOCKED`로 보존한다.

실행 DB에는 생성 전 container 이름·소유 토큰·Run ID를 기록하고, 생성 뒤 전체 ID를 저장한다. 실제 container에는 소유 토큰과 Run label을 함께 붙인다. 복구는 이름·토큰·Run label·기록한 ID가 일치하는 자기 container만 종료·제거한다. 이름 조회가 실패하면 기록한 ID로도 잔존 여부를 확인한다. 생성 결과가 불확실하고 ID도 없으면 단순 부재를 정리 완료로 인정하지 않는다. 과거 3-C의 미완 Run에 이 정보가 없으면 `legacy_untracked`와 `BLOCKED`로 기록하고 광범위 label 조회·kill로 대신하지 않는다.

파일 변경은 짧은 비동기 FS guard에서 요청 fence를 확인하고 취소 writer와 직렬화한다. 제어 commit이 앞서면 파일 작업을 시작하지 않고, 이미 시작한 짧은 파일 작업이 있으면 그 작업이 끝난 뒤 제어를 commit한다. Docker create/start는 별도 동기 dispatch 트랜잭션에서 generation을 재확인하고 실제 CLI spawn까지 직렬화한다. RPC 완료는 잠금 밖에서 기다린다. 취소 전에 전달된 RPC와 이미 바뀐 파일은 취소로 되돌아가지 않으며 controller의 polling·정리 또는 명시적 복구 대상으로 남는다.

`execution-recover`는 실행을 재개하지 않고 영속한 lifecycle과 작업 영역 증거를 조사한다. 부분 파일·추적/미추적 변경·삭제·권한·Git·실행 view를 새 프로세스에서 확인한다. 링크를 따라가거나 권한을 고치지 않고 파일 수·바이트 한도를 적용한다. 예상 밖 이름은 해시로 보고하며 그 파일의 본문을 읽지 않는다. 정리·관찰이 확인되면 `INTERRUPTED` 또는 `CANCELLED`, 미확인이면 `BLOCKED`다. 소비 승인 `usedAt`은 유지한다. 이미 `BLOCKED`인 Run은 재조사 뒤에도 역사를 덮어쓰지 않고 lifecycle의 cleanup·observation만 갱신한다. 실행 단계 이력과 제어 이벤트는 추가 전용 테이블로 보존한다.

`execution-inspect`는 Task·요청 상태·승인 페이지·Run·lifecycle을 단일 DB snapshot으로 읽고 트랜잭션을 끝낸 뒤 보고서 파일을 다룬다. SQLite를 원본으로 누락된 완료 보고서만 만들고 다른 내용의 기존 보고서는 덮어쓰지 않는다. 제어·조회만 전역 lease를 우회하며 실행·복구는 계속 실시간 Slack 수신과 직렬화한다. 실제 Slack 편집·삭제를 합성 Task에 연결하지 않으며 수신 공백의 변경 감지도 보장하지 않는다. 자동 재실행·승인 복원·commit·push·작업물 삭제는 없다.

## 6. Slack과 외부 전송

### 최소 접근

허용된 워크스페이스와 필요한 채널만 연결한다. 앱이 접근 가능한 전체 대화를 자동 수집하지 않는다. 단계 2의 최소 manifest는 공개 채널 읽기만 요청하고, 비공개 채널은 별도 허용 시 추가하며 DM은 제외한다. 정확한 토큰 종류·scope·채널 멤버십·스레드 조회 권한은 실제 연결 시 공식 문서와 회사 설정을 확인한다. 구체적인 이벤트·scope와 공식 근거는 [단계 2 계획](implementation-plan.md#단계-2-slack-읽기-연결)에 둔다.

`liveReadEnabled`의 기본값은 `false`다. 실제 수신은 계정·워크스페이스·채널·자료 보관 정책이 별도로 승인된 환경에서만 켠다. 하네스 구현 요청은 실제 회사 계정 연결이나 회사 자료 반출 승인으로 확대하지 않는다. 설정의 승인 확인 값만으로 회사 승인 절차를 대체하지 않는다.

Slack 토큰·네트워크는 수신부에만 제공한다. 조사 worker에는 상속하지 않으며 기존 네트워크·child process 차단을 유지한다. 수신부는 필요한 읽기 API와 전달 확인 ACK만 사용한다. ACK에는 업무 답변을 담지 않고 `response_url`이나 임의 URL을 사용하지 않는다. 외부 모델과 Slack 쓰기 API는 수집 경로에 제공하지 않는다.

실수신 경로의 고정 API는 identity를 확인하는 `auth.test`, 연결을 여는 `apps.connections.open`, 해당 스레드를 읽는 `conversations.replies`다. 읽기 토큰의 workspace가 설정과 일치하지 않으면 Socket 연결과 문맥 수집을 시작하지 않는다. 이 검사가 실제 회사 승인·scope·채널 접근 권한 검증을 대신하지는 않는다.

수신부의 Node 네트워크 권한은 프로세스 전체에 적용된다. 목적지는 어댑터의 고정 Slack API·redirect 거부와 정확한 WSS 호스트 검증으로 제한한다. 이 검사를 호스트별 OS 네트워크 격리나 악성 코드 실행 sandbox로 설명하지 않는다. 토큰은 환경변수로만 주입하며 CLI 인자·설정 파일·저장 자료에 넣지 않는다.

사용자 멘션은 고정 사용자 ID로 확인한다. `app_mention`은 봇 멘션용이므로 사용자 멘션을 대신하지 않는다. 소유자 멘션이나 요청자의 긴급 표현은 실행 승인이 아니다.

### 이벤트 처리

- 허용 범위를 확인한 뒤 최소 자료와 이벤트 중복 키를 SQLite inbox에 commit하고 ACK한다. 저장 실패나 포화로 미보관한 새 메시지는 성공 ACK하지 않는다. 편집은 포화 상태에서도 기존 계획 무효화와 최신 요청의 `BLOCKED`·`SLACK_INBOX_FULL`을 commit한 뒤 ACK하며 새 문맥 수집만 생략한다. 비허용 입력은 본문을 저장하거나 작업으로 만들지 않는다.
- `envelope_id`는 전달별 ACK, `event_id`는 중복 제거, `(workspaceId, channelId, messageTs)`는 원본 메시지 식별에 사용한다. 재전달·ACK 실패·재시작으로 중복 수집하지 않는다.
- ACK 후 스레드를 제한적으로 읽는다. 페이지·메시지·응답 크기·시간·재시도 한도를 두고 `429`의 `Retry-After`를 지킨다. 불완전한 문맥을 완료 수집으로 보고하지 않는다.
- 봇·자기 메시지로 생기는 반복 처리를 막는다.
- 편집·삭제·멘션 제거는 해당 원본의 기존 작업을 취소하고 오래된 계획·보고를 제거한다. revision과 최소 tombstone으로 오래된 이벤트와 늦게 끝난 스레드 수집이 최신 상태를 되돌리지 못하게 한다.
- 확인된 같은 스레드 reply의 편집·삭제도 기존 문맥과 연계 작업을 무효화한다. root 불명 변경은 같은 채널의 `RECEIVED`이면서 pending·processing인 수집을 보수적으로 무효화한다. 이 때문에 무관한 진행 중 수집도 중단될 수 있지만 관련성이 확인되지 않은 완료 수집은 유지한다. 큐가 가득 차도 삭제·멘션 제거와 편집의 기존 계획 무효화는 반영한다. 취소 보고서 파일은 DB 상태에 따라 다시 쓰며 실패·중단 시 다음 명령에서 복구한다.
- disconnect·재연결 공백은 누락 가능 구간으로 기록하고 최근 100개 연결·공백 상태를 DB에 보관한다. 수집 누락을 숨기거나 채널 전체 기록을 자동 backfill하지 않는다.
- ACK 핸들러는 문맥·보고서 I/O를 기다리지 않는다. 종료 시 HTTP·재시도 대기·Socket·후속 작업을 취소·정리한 뒤 DB를 닫는다. 중단된 processing은 자동 재수집 없이 차단 상태로 남긴다.

단계 2 수신 기록의 분석은 `not_run`이다. 실제 메시지를 고정 모델에 넣어 합성 코드 근거와 업무 답변을 자동으로 생성하지 않는다. 모델 분석을 붙이려면 실제 자료의 처리 목적·제공자·정책과 검증을 별도로 정한다.

### 전송 분리

로컬 보고서 출력과 Slack 메시지 전송을 서로 다른 경로로 둔다. 초기 외부 전송 어댑터는 비활성화하고, 모델·보고서 내용만으로 활성화하지 못하게 한다.

Slack 메시지 전송, 외부 모델 호출, Git 원격 변경은 서로 다른 목적지와 자료를 다루므로 각각 정책을 검사한다. 코드 변경 승인은 어느 전송에도 포괄적인 허가가 아니다.

### 단계 4-A의 합성 답장 승인과 모의 전송

이 단계의 구현은 2026-11-11의 후속 개발 요청에 한정한다. 실제 Slack 쓰기 권한·토큰·네트워크를 추가하지 않는다. 합성 `W_LOCAL`·`C_ALLOWED`의 원래 요청 스레드와 코드에 고정한 일반 텍스트 요약만 계획으로 만든다. 임의 본문·다른 수신자·DM·첨부·알림 멘션·코드 전문·모델 출력·저장소 자료는 답장 입력으로 받지 않는다. 고정 본문 일치, 본문 해시·바이트 수와 지원 비밀/개인정보 패턴을 검사하며 이를 실제 회사 자료의 분류 정책으로 간주하지 않는다.

`ReplyPlan`은 `synthetic-reply-v1`·`mode: mock`, OS 소유자, 원래 요청 ID·workspace/channel/message/thread·요청자·요청/문맥 revision·완전성·공백·만료, 목적지, 본문 해시·바이트 수, 생성·만료 시각과 보관 정책에 결합한다. 승인 전 `reply-plan` 또는 `reply-inspect`에서 정확한 대상·유효 본문·계획 해시를 확인한다. 소유자는 현재 OS UID의 `os-user:<uid>`이며 UID 미지원·다른 소유자를 거부한다. 승인 입력은 정확한 `planHash`와 필수 정수 TTL 1~60분이다. 기본값은 없고 30분을 권장하며 만료는 본문/source 만료 이내로 제한한다. 합성 source는 생성 후 24시간 동안 유효하므로 본문 보관 설정이 더 길어도 계획·본문 유효기한은 최대 24시간이다.

별도 `replies.sqlite`를 사용하며 기존 `tasks.sqlite`·`execution.sqlite`·Slack inbox의 승인과 작업을 전송에 사용하지 않는다. 승인 생성과 `APPROVED` 전환, 승인 소비·Task `SENDING`·전송 시도 생성은 각각 같은 SQLite 트랜잭션이다. 소비한 승인 `usedAt`은 실패해도 복원하지 않는다. 계획/본문/목적지 변조, 요청·문맥 revision 변화, 새 reply와 취소는 기존 승인을 무효화한다. 불완전·공백·만료·최신성 미확인은 승인과 전송을 막는다. 합성 이벤트의 중복 ID·동일 payload는 멱등 처리하고 다른 payload 재사용·오래된 revision을 거부하거나 무시하여 상태를 되돌리지 못하게 한다.

가짜 어댑터 성공은 `SIMULATED`이며 실제 Slack 전송 성공이 아니다. 확실한 미전송은 시도 `NOT_SENT`와 Task `FAILED`로 남기고, 새 승인으로만 수동 재시도한다. 자동 재시도는 없다. 불확실한 결과·어댑터 예외와 `SENDING`의 무효화는 `UNKNOWN`으로 남기며 다시 승인하거나 전송하지 않는다. 승인 소비 이후 DB 종료·프로세스 중단으로 남은 `SENDING`은 문맥이 유효하면 시작·조회 시 그대로 보존하고 명시적 `reply-recover`로 `UNKNOWN`을 확정한다. 별도 본문/source 만료·무효화도 진행 중 시도를 `UNKNOWN`으로 차단한다. 복구는 멱등이며 전송 재개·승인 소비 복원을 하지 않는다. 늦은 취소는 이미 수행한 모의 결과를 되돌리지 않는다.

모든 `reply-*` 명령은 기존 전역 lease를 사용한다. 실시간 Slack 수신과 동시에 실행하지 않고 수신 공백 중 실제 요청 변경을 감지한다고 주장하지 않는다. 답장 worker는 Node 권한 모델로 하네스 읽기·비공개 데이터 디렉터리 쓰기만 허용하며 네트워크·하위 프로세스·추가 worker·외부 native addon 권한을 주지 않는다. 환경은 `LANG`·`TZ`만 전달하며 토큰을 상속하지 않는다. DB와 저널은 소유 UID·비공개 권한·symlink/hardlink를 검사한다. 이는 같은 OS 사용자와 신뢰하는 하네스 코드 안의 경계이며 악성 호스트·관리자 권한으로부터의 격리는 아니다.

본문은 별도 만료 payload에만 저장하며 승인 snapshot·전송 시도·영속 보고서에 복제하지 않는다. `bodyRetentionHours`는 기본 24시간·1~168시간이며 실제 만료는 source의 24시간 기한과 비교해 더 짧게 정한다. `reply-plan`·`reply-inspect`만 유효 본문을 stdout에 표시하고 승인·전송·취소·무효화·복구 출력에는 본문을 넣지 않는다. 사용자가 redirect한 stdout의 보관·삭제는 사용자의 정책을 따른다.

감사 기록은 본문 없이 계획/본문 해시·목적지·revision·소유자·승인·제어·시도 결과를 남긴다. `auditRetentionDays` 기본 `null`은 이 합성 metadata를 DB 수명 동안 보관한다는 뜻이며 회사 정책의 기본값이 아니다. 1~3650일을 명시하면 terminal 작업의 감사 기한이 지난 뒤 metadata를 제거하되 최소 task ID·계획 해시 중복 marker는 DB 수명 동안 유지한다. 진행 중 작업은 감사 정리로 제거하지 않는다. 만료 본문·감사 정리는 각 답장 명령 시작과 `reply-prune`에서 수행하므로 프로그램 중지 중에는 다음 실행까지 남을 수 있다. 논리 삭제는 물리적 완전 삭제를 보장하지 않으며 DB 폐기 뒤 과거 중복 차단도 보장하지 않는다. 실제 회사 도입 전에는 이 metadata 범위·DB 폐기·백업을 포함한 별도 보관 정책이 필요하다.

### 단계 4-B-1의 오프라인 HTTP 계약 진단

`slack-post-check`는 실제 Slack 쓰기를 연결하지 않는 계약 진단이다. `slack-post-contract-v1`·`offline-http`의 intent는 설정 hash·합성 대상·본문 hash·요청 revision·문맥 hash·만료를 묶는 검증 입력이며, 소유자의 전송 승인이나 영속 승인 소비를 대신하지 않는다. 단계 4-A의 `synthetic-reply-v1`·`mode: mock` 계획/승인과 기존 코드·실행 승인을 받아들이지 않는다. 기존 승인 DB는 열거나 바꾸지 않고 진단 통과를 활성화 토큰으로 저장하지 않는다.

`liveEnabled`는 `false`로 고정하고 기본 HTTP 포트는 요청을 0회 수행한다. 진단에서 합성 포트를 명시적으로 주입할 때만 고정 합성 workspace/channel/bot/user·thread·본문과 가짜 token으로 `auth.test`·`conversations.replies`·`chat.postMessage` 요청 직렬화를 검증한다. 실제 토큰/설정/본문/대상 입력과 실전송 활성화 옵션, 전역 `fetch`를 사용하는 실제 transport는 제공하지 않는다. 실제 승인된 계정·토큰이나 회사 자료를 fixture로 사용하지 않는다.

identity·요청 revision·문맥 hash·완전성·만료를 재검증하고 새 reply·불완전·만료·identity 불일치가 있으면 post 전 차단한다. 요청에는 고정한 스레드의 일반 텍스트와 확장 제한만 포함하고 redirect를 거부한다. 요청 제한 250ms·응답 16KiB를 적용하며 자동 재시도는 없다. 합성 성공 응답의 channel·message·thread·bot·본문을 대조한 결과는 `OFFLINE_CONFIRMED`다. 확실한 미전송은 `NOT_SENT`, post 이후 서버 오류·timeout·malformed/oversized 응답·receipt 불일치는 `UNKNOWN`으로 분리한다. 이 상태는 HTTP 계약 진단 결과이며 실제 메시지 전달이나 운영 중복 방지를 보장하지 않는다.

NestJS application context의 제한 worker는 하네스 읽기·비공개 데이터 디렉터리 쓰기만 허용하고 네트워크·하위 프로세스·추가 worker·외부 native addon 권한과 호스트 토큰을 받지 않는다. 가짜 token·본문·원시 HTTP 응답은 메모리에서만 사용하며 stdout과 `<data-dir>/slack-post-checks/<verificationId>/report.json`에 복제하지 않는다. 보고서에는 진단/receipt metadata·해시·정적 원인·호출 횟수와 `passed`·`failed`·`not_run`을 남긴다. 합성 진단 metadata의 로컬 보고서 보관은 실제 회사 보관 정책의 기본값이 아니다.

실제 전송은 아래 4-B-2의 별도 정책·저장소·승인을 사용한다. 이 합성 진단의 thread 재조회는 실제 수신 공백·문맥 경합을 해결하지 않는다. 4-A 승인과 4-B-1 intent/성공 보고서를 실전송 권한으로 재사용하지 않는다.

### 단계 4-B-2의 고정 시험 문구 단건 전송

`slack-live-test-v1`은 허가된 개인 테스트 workspace의 공개 채널·root 스레드 하나만 다루며 `live-replies.sqlite`를 사용한다. 기본 live 활성화는 `false`다. 기존 코드·실행·mock 승인과 오프라인 진단 intent/성공 보고서는 live 계획이나 승인으로 전환하지 않는다. 실제 대상 ID는 로컬 CLI와 비공개 DB metadata로 관리한다. token은 환경 주입 또는 TTY 숨김 입력으로만 받고 설정 파일에는 넣지 않는다. 실제 ID·token·런타임 DB는 fixture·Git에 넣지 않는다. 회사 계정·자료와 자동 업무 답장은 이 단계의 허가 범위가 아니다.

허용 원문은 `하네스 전송 테스트`라는 root 메시지 한 개이고 reply가 없어야 한다. 전송 본문은 코드의 고정 일반 텍스트 `하네스 Slack 단건 전송 테스트입니다. (4-B-2)`뿐이다. 본문·파일·URL에서 임의 전송 내용을 받지 않는다. 첨부·DM·계획에 고정한 대상 외 채널 전송·알림 멘션·링크 확장·Slack 수정/삭제 API를 제공하지 않는다. 게시 메시지 보관은 해당 Slack workspace 정책을 따른다.

plan·approve·send는 `auth.test`와 `conversations.replies`를 재호출해 workspace/bot/user와 원래 root, 고정 원문, raw revision·문맥 hash·완전성을 확인한다. source는 관측 시각·revision·hash·identity metadata만 저장하고 Slack 원문은 저장하지 않는다. 5초 이내 관측만 승인 생성·전송에 사용할 수 있다. 원문 편집·삭제·새 reply·부분 조회·만료·identity 변경을 확인하면 차단한다. 같은 데이터 디렉터리의 실시간 수신과 live 명령은 전역 lease로 직렬화한다. 이 경로는 수신 이벤트의 완전한 추적이나 Slack 조회와 POST의 원자성을 보장하지 않는다. 마지막 조회와 실제 게시 사이 외부 변경은 막을 수 없으며, 5초 이내 확인만 사용하는 단건 시험의 한계로 명시한다.

계획은 정책·설정을 포함한 계획 hash·OS UID 소유자·목적지·source identity·본문 hash·생성/만료를 묶으며 최대 24시간 유효하다. 소유자는 검토한 정확한 계획 해시에 기본값 없는 정수 TTL 1~60분을 지정해 새 live 승인을 만든다. 30분을 권장하고 계획 만료를 넘지 않는다. 승인만으로 전송하지 않는다. send는 저장소 트랜잭션에서 승인 소비·`SENDING` 시도·작업 상태를 함께 commit한 뒤 POST를 최대 한 번 호출한다.

channel·새 message timestamp·thread·bot·본문이 일치하는 성공 receipt만 `SENT`다. 명백한 API 거부·rate limit은 `NOT_SENT`/`FAILED`이며 새 승인으로만 수동 재시도한다. POST 이후 timeout·서버 오류·redirect·응답 형식/크기 오류·receipt 불일치는 `UNKNOWN`이다. `recover`는 중단된 `SENDING`을 `UNKNOWN`으로 확정하며 자동 재전송·소비 승인 복원은 없다. `SENT`·`UNKNOWN`은 workspace/channel/root 키의 최소 중복 marker를 DB 수명 동안 남겨 다른 task ID의 새 계획도 막는다.

실제 HTTP는 고정한 세 API만 사용하고 요청 10초·응답 32KiB·redirect 거부·자동 재시도 0을 강제한다. `SLACK_SEND_TOKEN` 환경 주입 또는 TTY 숨김 입력으로 받은 자격증명은 plan·approve·send worker에만 전달하며 argv·설정·DB·stdout·보고서·오류에 기록하지 않는다. inspect/list/cancel/recover/prune에는 token·네트워크를 주지 않는다. Node 권한으로 하네스 읽기·비공개 데이터 쓰기를 제한하고 child process·추가 worker·불필요한 호스트 환경을 차단한다. 어댑터의 고정 URL 검사는 호스트별 OS 네트워크 격리나 악성 코드용 sandbox와 다르다.

고정 전송 본문도 DB·승인 snapshot·시도·영속 보고서에 복제하지 않는다. 계획 유효기간 안에서 코드 상수로 재구성해 검토한다. terminal 감사 metadata는 마지막 상태 변경부터 30일 뒤 정리하고 `SENT`·`UNKNOWN`의 최소 대상 marker는 유지한다. 정리는 명령 실행 시 수행하므로 중지 중 만료 자료는 다음 실행까지 남을 수 있으며 논리 삭제는 백업·디스크의 물리적 완전 삭제를 보장하지 않는다. DB 폐기 뒤에는 과거 중복 차단을 보장할 수 없다.

구현 검사와 실제 게시는 구분한다. 단위·통합·CLI의 합성 응답 검증을 통과해도 실제 전송 권한이 생기지 않는다. 실제 게시 전에는 대상·고정 본문·계획 해시·TTL을 구체적으로 검토하고 별도 소유자 승인을 받아야 한다. 개인 테스트 workspace에서 이 절차를 거친 실제 단건 시험은 로컬 `SENT` 시도 한 개·승인 소비 한 번과 Slack UI의 댓글 한 개·고정 본문·receipt 일치로 확인했다. 이 확인은 회사 운영·자료·AI·실제 업무 자동 답장의 승인이 아니다. 검증 상태는 [4-B-2 결과](stage-4b2-result.md)를 따른다.

### 단계 4-C-1의 오프라인 브랜치 계약

`synthetic-branch-v1`·`offline`·`simulate-branch` 계획과 `branches.sqlite`는 모의 검증 전용이다. 작업 유형별 브랜치명과 고정 합성 source의 repo/remote/base/diff를 hash에 결합하며 실제 저장소 경로·임의 브랜치명·원격·명령·모델 출력을 받지 않는다. 커밋·diff hash는 실제 Git 객체를 검증한 증거가 아니다. 기존 조사·실행·Slack 승인과 DB는 사용하지 않는다.

OS UID 소유자·정확한 계획 hash·필수 정수 TTL 1~60분을 검증하며 계획은 최대 24시간 유효하다. 승인 소비·작업 `SIMULATING`·시도 생성은 한 트랜잭션이다. 작업당 모의 시도는 한 번이며 실패·중단 뒤에도 소비 승인을 복원하지 않는다. 확정 모의 성공 `SIMULATED`, 충돌 `NOT_CREATED`/`FAILED`, 불확실 `UNKNOWN`을 구분한다. 변경·취소가 진행 중 시도를 무효화하면 `UNKNOWN`으로 확정하고 늦은 결과를 거부한다. 시작·조회는 자동 실행하지 않고 명시적 복구는 중단된 `SIMULATING`을 `UNKNOWN`으로 전환한다.

모든 명령은 전역 lease·비공개 DB/sidecar의 소유자·권한·symlink/hardlink 검사를 사용한다. worker는 최소 환경과 데이터 디렉터리 쓰기만 받고 네트워크·child·추가 worker·외부 native addon 권한과 상속 토큰을 차단한다. source·승인 snapshot·모의 receipt·제어 이력은 합성 metadata로 DB 수명 동안 남으며 자동 정리는 제공하지 않는다. 같은 OS 사용자와 하네스 코드는 기존처럼 신뢰한다.

실제 Git·Codex·외부 모델·회사 저장소는 연결하지 않는다. commit·push·PR/MR 명령은 제공하지 않고 모의 승인을 실제 작업 권한으로 승격하지 않는다. 실제 연결에는 새로운 실행 정책·승인·격리·자료 처리 검증이 필요하며, [4-C-1 결과](stage-4c1-result.md)의 모의 통과를 그 검증으로 대신하지 않는다.

### 단계 4-C-2의 독립 합성 Git 작업

`local-synthetic-branch-v1`·`local-synthetic`·`create-branch`와 별도 `git-branches.sqlite`를 사용한다. 기존 4-C-1 모의 승인이나 코드 실행·Slack 승인을 실제 ref 생성에 사용하지 않는다. plan은 작업 유형과 private data directory만 받아 고정 합성 source/workspace를 배타적으로 준비한다. 회사/사용자 저장소 경로·원격·브랜치명·코드·명령은 입력으로 열지 않는다. 두 저장소의 초기 commit은 합성 fixture 준비이며 승인 후 변경을 commit하는 기능이 아니다.

작업 root는 `<data-dir>/git-branches/<task-id>`로 고정하고 정확한 경로·OS UID·소유 manifest·token을 확인한다. source와 workspace는 Git 객체·hardlink·공유 `.git` 없이 각각 초기화한다. source의 파일 `0444`·디렉터리 `0555`를 유지하고 workspace도 기본 동결하되 `.git/refs/heads`와 새 유형 디렉터리만 `0700`, 생성 ref만 `0600`을 허용한다. source/workspace의 파일 목록·owner·권한·symlink/hardlink·엔트리 수·총 바이트를 먼저 검사한 뒤 nofollow와 전후 metadata 확인을 사용해 제한된 읽기를 수행한다. 예상 밖 파일의 본문·이름은 출력하지 않으며 원시 파일 오류도 정적 코드로 바꾼다.

계획 hash는 작업 root·token·작업 유형·브랜치명·실제 기준 커밋·source/workspace hash·소유자·정책·24시간 유효기간을 결합한다. 정확한 planHash와 필수 정수 TTL 1~60분으로 새 승인을 만들며 승인 만료는 계획 만료 이내다. 승인과 실행 직전에 모든 경계와 ref 부재를 재검증한다. 동일 OID를 가리키는 ref도 이미 존재하면 생성하지 않는다. source·HEAD·main·기존 Git metadata는 유지하며 계획 ref와 선택적인 유형 디렉터리만 정규화 hash에서 제외한다.

승인 소비·`RUNNING`·`claimed`를 한 트랜잭션으로 저장한다. `writing` 단계와 시작 시각을 먼저 기록하고 짧은 동기 DB guard에서 generation을 확인한 뒤 ref를 배타적으로 생성하며 `O_SYNC`로 동기 쓰기를 요청한다. Node 제한 worker에서 `fsyncSync`가 허용되지 않으므로 해당 호출을 위해 권한을 확장하지 않는다. 프로세스 중단 복구를 검증하며 디렉터리 fsync·OS/전원 장애 내구성은 보장하지 않는다. 생성 뒤 `created`와 `refCreatedAt`, 완료 뒤 `finishedAt`과 전후 관찰을 저장한다. 취소·실패·중단 뒤 승인 소비를 복원하지 않으며 작업당 시도는 한 번이다. 대기 취소는 승인 revoke와 `CANCELLED`를 함께 반영하고, `RUNNING` 취소는 generation fence를 세워 이후 쓰기를 막으며 이미 만든 ref는 보존한다.

시작·inspect는 중단된 `RUNNING`을 유지한다. 명시 recover는 소유 identity·저장된 단계·현재 작업 영역을 확인하고 `INTERRUPTED`, 취소 기록이 있으면 `CANCELLED`, 경계 미확인은 `BLOCKED`로 보고한다. 정확한 ref가 관찰되더라도 성공으로 소급하지 않고 반복 복구는 기존 기록을 보존한다. 빈 유형 디렉터리는 부재, 부분 ref는 unsafe이며 자동 수리·재생성·ref 삭제는 하지 않는다.

모든 CLI는 같은 data directory의 전역 lease를 사용하므로 실행 중 별도 CLI cancel은 lease와 경합한다. 내부 generation fence가 실시간 CLI 인터럽트나 대상 요청의 지속 감지를 보장하지 않는다. 제한 worker는 최소 환경·하네스 읽기·private data directory 쓰기만 받고 네트워크·child·추가 worker·상속 token을 차단한다. 합성 작업물과 감사 기록을 자동 정리하지 않는다. 파일 권한·소유 manifest·Node 권한은 같은 OS 사용자와 신뢰하는 하네스라는 경계 안에서 동작하며 악성 코드용 sandbox나 회사 보안 검토 통과를 뜻하지 않는다. 실제 Codex·회사 자료·checkout·코드 변경·작업 결과 commit·push·PR/MR은 별도 실행 경로로도 제공하지 않는다.

## 7. 회사 자료와 비밀정보

회사 계정·저장소 연결 전에 AI 제공자, 모델, 실행 위치, 전송 가능 자료, 보관 기간과 감사 요구를 회사 정책에 따라 확인한다. 회사 승인이 없으면 합성 데이터로 계속 개발한다.

- 회사의 소프트웨어 반입 절차를 따른다. 하네스의 범용 코드만 회사 환경으로 가져가고, 회사 코드·설정을 개인 원격 저장소로 보내지 않는다.
- 실제 토큰, 사용자 설정, SQLite, 승인 기록, 원문 메시지, 보고서, 로그와 worktree를 커밋하지 않는다.
- `.env.example`과 fixture에는 명백한 가짜 값만 사용한다. 실제 회사 코드, 비공개 대화와 고객 자료를 합성 fixture로 위장하지 않는다.
- 자격증명은 승인된 비밀 저장소에 두고 필요한 프로세스에만 제공한다. 개인·회사 계정의 자격증명, 캐시와 보고서를 분리한다.
- 모델에는 작업에 필요한 최소 자료만 보낸다. 토큰·키가 입력, 오류 메시지, diff, 보고서와 로그에 포함되지 않도록 검사한다.
- 보고서와 실행 로그도 회사 정보를 포함할 수 있다. 저장 위치·열람 권한·마스킹·보관·삭제 정책을 정한다.
- 단계 2에서는 알려진 비밀 패턴과 지원하는 이메일·전화번호 패턴을 저장 전에 마스킹하고 원문 프레임·blocks·첨부파일을 통째로 저장하지 않는다. 이 패턴 검사는 모든 개인정보를 판별하지 못하므로 실제 회사 자료 처리의 승인 근거로 쓰지 않는다.
- 단계 2 메시지·문맥 payload에는 `retentionHours` 1~168시간, 기본 24시간을 적용하고 수신·조회·정리 시 만료 자료를 제거한다. 이벤트 중복 키, 원본 ID·revision·삭제 marker는 DB 수명 동안 유지하며 본문 만료 뒤 같은 이벤트가 자료를 되살리지 못하게 한다. 최소 metadata는 보관 기한 뒤에도 남으므로 회사 승인 시 이 범위와 DB 폐기 정책을 함께 확인한다.
- SQLite의 논리적 삭제는 백업·파일시스템·디스크의 물리적 완전 삭제를 보장하지 않는다. DB 폐기 후에는 과거 중복·순서 보존도 보장하지 않는다. CLI 출력을 별도 파일로 내보낸 경우에는 사용자가 정한 보관 정책을 적용한다.
- `.gitignore`는 커밋 실수를 줄이는 수단일 뿐 접근 통제나 유출 방지 장치 전체를 대신하지 않는다.

Gmail·Calendar·Drive는 후속 선택 기능이다. 연결된 계정이 있다는 이유로 전체 자료를 읽지 않는다. 읽기 범위와 보내기·일정 변경·파일 수정·공유 권한을 각각 정의한다.

## 8. 취소, 실패와 감사 기록

실행 전 취소는 대기 작업을 종료한다. 실행 중 취소는 새 동작을 막고 실행 중인 프로세스를 종료한 뒤, 이미 바뀐 파일과 남은 영향을 보고한다. 취소가 이미 보낸 메시지나 원격 변경을 되돌린다고 가정하지 않는다.

실패와 재시작 때 작업 상태, 잔여 diff, 승인 사용 기록을 보존한다. 검사별로 `passed`, `failed`, `not_run`과 이유를 남긴다. 재개는 현재 상태와 승인 범위를 확인한 후 결정하며 자동으로 반복 실행하지 않는다.

감사 기록에는 누가 어느 계획을 승인했는지, 어떤 정책 검사를 통과·실패했는지, 무엇을 실행했고 어떤 결과였는지를 남긴다. 원문 대화·코드 전문·비밀값을 무조건 기록하지 않는다.

## 9. 보안 검증의 완료 조건

다음 경계는 실제 실패 테스트로 확인한다.

- 승인 전 대상 파일 변경과 대상 스크립트 실행이 없음.
- 비허용 경로·symlink·비밀 파일이 모델 입력과 로그까지 도달하지 않음.
- 외부 자료의 악성 지시와 잘못된 모델 JSON이 권한 변경·명령 실행을 만들지 못함.
- 만료·취소·위조·중복 승인, 변경된 계획·커밋·요청 revision을 거부함.
- 취소·재시작 후 자동 재실행이 없고 잔여 작업물이 보존됨.
- 별도 허가 없는 메시지 전송·push가 없고, 대상 저장소 작업에 PR/MR 생성 경로를 제공하지 않음.
- 승인 범위 밖 변경과 실패·미실행 검사를 성공으로 보고하지 않음.

단계 3-A의 기록용 승인, 단계 3-B의 합성 격리 진단, 단계 3-C의 독립 합성 실행, 단계 3-D의 합성 제어·복구, 단계 4-A의 합성 답장 전용 승인, 단계 4-B-1의 오프라인 HTTP 계약 진단과 단계 4-B-2의 별도 live 승인을 구분한다. 실제 검증 범위는 각 결과 문서에서 `passed`, `failed`, `not_run`으로 기록한다. 기존 조사 실행 포트는 항상 거부하며 실제 회사 저장소·Slack 요청 실행·자동 업무 답장은 연결하지 않는다. 실제 Slack 게시 검증은 별도 승인된 고정 단건 시험으로만 기록한다. 합성 검증을 회사 보안 검토 통과로 표현하지 않는다. 상세 수용 테스트는 기준 계획서에서 관리한다.
