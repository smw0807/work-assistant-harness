# 보안과 승인 경계

## 문서의 목적과 상태

이 문서는 구현할 보안 요구사항이다. 문서를 작성하거나 `AGENTS.md`에 규칙을 넣었다는 이유로 보호 장치가 작동한다고 간주하지 않는다. 코드, 권한 설정과 실패 테스트로 검증한 기능만 사용한다.

단계 0·1의 구현과 테스트 결과는 [stage-1-result.md](stage-1-result.md), 단계 2 수신 어댑터·CLI·오프라인 테스트는 [stage-2-result.md](stage-2-result.md), 단계 3-A의 로컬 승인·취소와 영속 기록은 [stage-3a-result.md](stage-3a-result.md)에 기록한다. 단계 3-A는 실제 실행을 열지 않는다. 현재 Node 권한 모델은 신뢰하는 하네스 코드의 접근 제한이며, 후속 단계의 악성 코드 실행용 보안 격리를 충족했다고 주장하지 않는다.

전체 흐름은 [architecture.md](architecture.md), 단계와 상세 수용 테스트는 [implementation-plan.md](implementation-plan.md)를 따른다. 초기 범위는 합성 데이터 기반의 로컬 조사이며 실제 회사 계정과 코드를 연결하지 않는다.

## 1. 신뢰 경계

- **소유자:** 로컬 CLI에서 표시된 계획을 검토하고 실행을 승인하는 사람.
- **요청자:** Slack에서 문의나 변경 요청을 보낸 사람. 요청은 조사 대상이며 소유자의 실행 승인이 아니다.
- **모델:** 분류·설명·계획을 제안한다. 권한을 만들거나 변경하지 못한다.
- **외부 자료:** Slack 본문, 저장소 파일, README, 코드 주석과 도구 출력. 그 안의 명령문은 신뢰할 실행 지시가 아니다.
- **정책과 실행 환경:** 실제 접근, 명령과 전송 여부를 강제한다. 모델 출력은 이 경계를 우회할 수 없다.

MVP의 승인 경로는 로컬 CLI뿐이다. 현재 OS 사용자와 승인 저장소의 파일 권한이 신뢰 경계다. 같은 OS 계정을 공유하거나 호스트가 침해되면 이 가정이 깨질 수 있으므로 다중 사용자 원격 승인 서비스와 동등한 인증을 제공한다고 주장하지 않는다.

단계 3-A의 소유자 ID는 `process.getuid()`가 반환한 `os-user:<uid>`로 고정한다. CLI 옵션이나 Slack ID로 소유자를 지정하지 않는다. UID가 지원되지 않으면 승인·취소를 거부한다. 승인·취소는 기존 전역 lease를 요구하므로 같은 데이터 디렉터리의 실시간 Slack 수신 중에는 수행하지 않는다. 이 제한은 오프라인 승인 기능의 한계이며 수신 중단 동안의 요청 변경 감지를 보장하지 않는다.

## 2. 행위별 승인

| 행위 | 조건과 경계 |
| --- | --- |
| 하네스 자체의 개발·검증 | 요청된 개발 범위에서 진행한다. 대상 제품 저장소의 수정 권한으로 확대하지 않는다. |
| 대상 코드 읽기·초안 작성 | 사전 허용된 저장소·커밋·경로와 데이터 처리 범위 안에서만 한다. 대상 파일 수정이나 스크립트 실행은 포함하지 않는다. |
| 대상 코드 변경·검사 실행 | 단계 3 이후, 구체적인 계획에 대한 유효한 소유자 승인을 **실제 변경이나 실행 전에** 확인한다. |
| 의존성 설치·테스트 설정 변경 | 실행 코드와 외부 연결을 수반할 수 있으므로 계획에 별도로 명시한다. 코드 수정 승인에 묵시적으로 포함하지 않는다. |
| 요청자 답장·소유자 Slack DM | 기본 비활성화. 수신자·채널·전송 내용 또는 명확한 내용 범위를 별도로 허용받는다. 로컬 보고서 생성은 전송 승인이 아니다. |
| Git push·PR 생성 | 초기 범위 밖이다. 원격·브랜치·대상 diff와 PR 정보를 별도로 승인받는다. 로컬 변경 승인을 재사용하지 않는다. |
| 병합·배포 | 첫 버전에서 구현하지 않는다. 후속 도입 시 독립된 승인과 운영 정책을 정한다. |
| 회사 자료를 외부 AI로 전송 | 회사가 허용한 제공자·실행 위치·자료 범위·보관 조건이 먼저 충족되어야 한다. 개인의 수정 승인이 회사의 데이터 반출 승인을 대신하지 않는다. |

권한이 불명확하거나 정책 검증이 실패하면 해당 동작을 차단한다. 정책 오류를 기본 허용으로 바꾸거나 다른 도구로 우회하지 않는다.

## 3. 승인 전 보여 줄 계획

소유자가 무엇을 허용하는지 확인할 수 있도록 다음 내용을 함께 표시한다.

- 작업 ID, 대상 저장소 ID와 기준 커밋.
- 원래 요청과 메시지 revision, 목적과 기대 동작.
- 수정할 파일 또는 좁은 경로 범위와 허용할 변경.
- 실행할 등록 명령 ID와 인자, 설치·외부 연결 필요 여부.
- 예상 위험, 한계와 검사 계획.
- 계획 버전과 해시, 승인 만료 시각과 취소 방법.

승인 유효기간은 설정값이다. 계획서의 30분은 예시이며 확정된 운영 정책으로 하드코딩하지 않는다.

단계 3-A CLI에서는 `--expires-in-minutes`를 필수로 받고 1~1440분의 정수만 허용한다. 이 입력 범위는 로컬 승인 기록의 한도이며 회사 운영 정책의 승인 근거가 아니다.

### 승인 기록과 소비

승인은 `ownerId`, `taskId`, `planHash`, `baseCommit`, 허용 동작, 만료 시각, 취소·사용 상태에 묶는다. `planHash` 계산에는 대상 저장소, 요청 revision, 허용 파일·명령 등 승인 대상 내용을 포함한다.

- 작업 ID만 일치하거나 모델이 실행을 권했다고 승인하지 않는다.
- 계획 내용, 저장소, 기준 커밋 또는 요청 revision이 바뀌면 기존 승인을 무효화한다.
- 실제 실행 직전에 기준 커밋과 모든 승인 조건을 재검증한다.
- 승인 소비와 `RUNNING` 전환은 원자적으로 처리한다. 동일 승인으로 중복 실행하지 않는다.
- 새 파일, 더 넓은 변경, 새 명령·인자 또는 다른 외부 연결이 필요하면 멈추고 새 계획을 제시한다.
- 중단된 실행의 결과가 불확실하면 상태와 작업물을 먼저 조사한다. 재시작 자체를 재실행 승인으로 취급하지 않는다.

단계 3-A는 아래 범위로 제한한다.

- 승인 불변 스냅샷에는 계획·해시·요청 revision·저장소·기준 커밋을 고정하고 별도 SQLite 테이블에 보존한다. 승인 생성과 `APPROVED` 전환은 같은 트랜잭션이며 활성 승인을 중복 생성하지 않는다.
- 만료 조정은 승인 취소와 `AWAITING_APPROVAL` 복귀를 함께 기록한다. 로컬 취소는 승인 대기·승인됨 변경 요청만 `CANCELLED`로 바꾼다. 요청 편집·삭제도 Task 무효화와 같은 트랜잭션에서 기존 승인을 취소한다. Task 계획·보고를 제거해도 불변 승인 스냅샷은 유지한다.
- `executionPolicy`는 `approval-only-v1`이며 `usedAt`은 `null`이다. 승인 소비·Run 생성·대상 수정과 검사는 구현하지 않는다. 후속 실제 실행 정책의 새 승인을 요구하며 이 기록을 재사용하지 않는다. `ExecutionPort`는 항상 거부하고 `run` 명령은 없다.
- 현재 기준 커밋 검증은 Task·계획·CLI 입력의 일치 검사다. 실제 대상 저장소의 실행 직전 상태 검증과 승인 소비의 원자성은 후속 단계에서 검증한다.

## 4. 읽기 전용은 권한으로 강제한다

“수정하지 말라”는 프롬프트와 실행 후 diff 검사만으로는 부족하다. 다음 제한을 구현하고 검증한다.

1. **대상 입력 고정:** 허용된 저장소와 기준 커밋의 스냅샷을 읽는다. 소유자의 기존 작업 디렉터리를 조사 중에 갱신·checkout·reset하지 않는다.
2. **도구 분리:** 조사 경로에는 읽기용 포트만 제공한다. 파일 쓰기, 임의 쉘, 패키지 실행과 Git 원격 도구는 제공하지 않는다. 기본 `ExecutionPort`는 항상 거부한다.
3. **쓰기 권한 분리:** 대상 소스는 읽기 전용 마운트나 동등한 파일시스템 권한으로 보호하고, 보고서·SQLite를 위한 쓰기 경로는 따로 둔다. 정책 검사가 실패했을 때도 대상 쓰기가 가능하지 않은지 검증한다.
4. **경로 검증:** 저장소 root와 실제 경로를 정규화하고 symlink, `..`, 절대 경로 등을 통한 root 밖 접근을 차단한다. 읽기 시점에도 허용 경로 안에 있음을 확인한다.
5. **자료 제한:** 허용 목록과 제외 규칙을 함께 적용한다. 비밀 파일, 개인 키와 자격증명, 불필요한 개인정보, 바이너리와 과도하게 큰 파일을 제외한다. 필요한 줄만 모델 입력에 넣는다.
6. **결과 검증:** 조회 전후 파일 해시와 상태를 비교한다. Git diff만으로 누락될 수 있는 새 파일과 추적되지 않은 파일도 고려한다. 이것은 방어 장치의 검증이지 쓰기 차단의 대체물이 아니다.

대상 저장소의 `package.json`에 있는 test·build·install도 임의 코드를 실행할 수 있다. 조사 단계에서는 실행하지 않는다. Git을 사용할 때도 필요한 읽기 동작만 제공하고 hooks나 외부 명령 실행 경로를 열지 않는다.

하네스 테스트를 위해 합성 저장소를 임시 경로에 준비하는 행위와 실제 조사 중 대상을 바꾸는 행위를 분리한다. “테스트용”이라는 이유로 회사 저장소나 소유자의 기존 변경을 사용하지 않는다.

## 5. 승인 후 실행의 격리

별도 브랜치와 worktree는 원래 작업 디렉터리와 변경을 분리하는 수단이다. **worktree는 보안 sandbox가 아니다.** Git 메타데이터를 공유하며 같은 OS 권한으로 다른 파일이나 네트워크에 접근할 수 있다.

실행 기능을 열기 전에 다음을 검증한다.

- 쓰기 가능한 경로를 승인된 작업 영역으로 제한하고, 원래 작업 디렉터리와 승인 저장소를 보호한다.
- 실행 프로세스에 개인·회사 자격증명, SSH 키, 클라우드 토큰 등 호스트의 비밀을 상속하지 않는다.
- 네트워크는 기본 차단한다. 필요한 연결은 계획과 정책에 목적지·용도를 좁혀 명시한다.
- 명령은 사전에 등록한 `commandId`와 인자 스키마로 선택한다. 모델이 만든 문자열을 셸 명령으로 실행하지 않는다.
- 인자, 실행 파일과 작업 디렉터리를 검증한다. 등록된 테스트도 저장소 코드를 실행하므로 격리 제한을 유지한다.
- 실행 시간, 메모리와 출력 크기를 제한하고 취소 시 하위 프로세스도 종료할 수 있게 한다.
- 승인된 파일 범위와 실제 diff를 비교한다. 승인되지 않은 변경, 외부 전송 시도 또는 검사 실패를 성공으로 표시하지 않는다.

기본 결과는 로컬 diff와 검사 보고다. 자동 commit, 자동 push, worktree의 자동 삭제와 실패 작업물의 자동 정리는 하지 않는다. 의도치 않은 변경을 발견해도 기존 사용자 작업을 지우는 방식으로 복구하지 않는다.

위 실행 격리는 단계 3-B 이후의 요구사항이다. 지원할 backend와 버전, 준비·검증 실패 시 거부 조건을 정하고 호스트 파일·원본·승인 DB·공유 Git 메타데이터·외부 통신 차단을 실제 환경에서 실증한 뒤 실행 기능을 연다. 단계 3-C는 고정 합성 patch부터 시작하고 명령의 실행 파일·argv·cwd·환경·네트워크·자원 한도와 정책 버전을 승인 계획에 묶는다. 단계 3-D는 실시간 수신과 실행 잠금·요청 무효화 경합, 프로세스 트리 취소와 crash 복구를 검증한다. 상세 순서와 수용 기준은 [단계 3 계획](implementation-plan.md#단계-3-승인-후-코드-변경)을 따른다.

## 6. Slack과 외부 전송

### 최소 접근

허용된 워크스페이스와 필요한 채널만 연결한다. 앱이 접근 가능한 전체 대화를 자동 수집하지 않는다. 단계 2의 최소 manifest는 공개 채널 읽기만 요청하고, 비공개 채널은 별도 허용 시 추가하며 DM은 제외한다. 정확한 토큰 종류·scope·채널 멤버십·스레드 조회 권한은 실제 연결 시 공식 문서와 회사 설정을 확인한다. 구체적인 이벤트·scope와 공식 근거는 [단계 2 계획](implementation-plan.md#단계-2-slack-읽기-연결)에 둔다.

`liveReadEnabled`의 기본값은 `false`다. 실제 수신은 계정·워크스페이스·채널·자료 보관 정책이 별도로 승인된 환경에서만 켠다. 하네스 구현 요청은 실제 회사 계정 연결이나 회사 자료 반출 승인으로 확대하지 않는다. 설정의 승인 확인 값만으로 회사 승인 절차를 대체하지 않는다.

Slack 토큰·네트워크는 수신부에만 제공한다. 조사 worker에는 상속하지 않으며 기존 네트워크·child process 차단을 유지한다. 수신부는 필요한 읽기 API와 전달 확인 ACK만 사용한다. ACK에는 업무 답변을 담지 않고 `response_url`이나 임의 URL을 사용하지 않는다. 외부 모델과 Slack 쓰기 API는 수집 경로에 제공하지 않는다.

실수신 경로의 고정 API는 identity를 확인하는 `auth.test`, 연결을 여는 `apps.connections.open`, 해당 스레드를 읽는 `conversations.replies`다. 읽기 토큰의 workspace가 설정과 일치하지 않으면 Socket 연결과 문맥 수집을 시작하지 않는다. 이 검사가 실제 회사 승인·scope·채널 접근 권한 검증을 대신하지는 않는다.

수신부의 Node 네트워크 권한은 프로세스 전체에 적용된다. 목적지는 어댑터의 고정 Slack API·redirect 거부와 정확한 WSS 호스트 검증으로 제한한다. 이 검사를 호스트별 OS 네트워크 격리나 악성 코드 실행 sandbox로 설명하지 않는다. 토큰은 환경변수로만 주입하며 CLI 인자·설정 파일·저장 자료에 넣지 않는다.

사용자 멘션은 고정 사용자 ID로 확인한다. `app_mention`은 봇 멘션용이므로 사용자 멘션을 대신하지 않는다. 소유자 멘션이나 요청자의 긴급 표현은 실행 승인이 아니다.

### 이벤트 처리

- 허용 범위를 확인한 뒤 최소 자료와 이벤트 중복 키를 SQLite inbox에 commit하고 ACK한다. 저장 실패나 포화로 미보관한 새 메시지는 성공 ACK하지 않는다. 편집은 포화 상태에서도 기존 계획 무효화와 최신 요청의 `BLOCKED`·`SLACK_INBOX_FULL`을 commit한 뒤 ACK하며 새 문맥 수집만 생략한다. 비허용 입력은 본문을 저장하거나 작업으로 만들지 않는다.
- `envelope_id`는 전달별 ACK, `event_id`는 중복 제거, `(workspaceId, channelId, messageTs)`는 원본 메시지 식별에 사용한다. 재전달·ACK 실패·재시작으로 중복 수집하지 않는다.
- ACK 후 스레드를 제한적으로 읽는다. 페이지·메시지·응답 크기·시간·재시도 한도를 두고 `429`의 `Retry-After`를 지킨다. 불완전한 문맥을 완료 수집으로 보고하지 않는다.
- 봇·자기 메시지로 생기는 반복 처리를 막는다.
- 편집·삭제·멘션 제거는 해당 원본의 기존 작업을 취소하고 오래된 계획·보고를 제거한다. revision과 최소 tombstone으로 오래된 이벤트와 늦게 끝난 스레드 수집이 최신 상태를 되돌리지 못하게 한다.
- 확인된 같은 스레드 reply의 편집·삭제도 기존 문맥과 연계 작업을 무효화한다. root 불명 변경은 같은 채널의 `RECEIVED`이면서 pending·processing인 수집을 보수적으로 무효화한다. 이 때문에 무관한 진행 중 수집도 중단될 수 있지만 관련성이 확인되지 않은 완료 수집은 유지한다. 큐가 가득 차도 삭제·멘션 제거와 편집의 기존 계획 무효화는 반영한다. 취소 보고서 파일은 DB 상태에 따라 다시 쓰며 실패·중단 시 다음 명령에서 복구한다.
- disconnect·재연결 공백은 누락 가능 구간으로 기록하고 최근 100개 연결·공백 상태를 DB에 보관한다. 수집 누락을 숨기거나 채널 전체 기록을 자동 backfill하지 않는다.
- ACK 핸들러는 문맥·보고서 I/O를 기다리지 않는다. 종료 시 HTTP·재시도 대기·Socket·후속 작업을 취소·정리한 뒤 DB를 닫는다. 중단된 processing은 자동 재수집 없이 차단 상태로 남긴다.

단계 2 수신 기록의 분석은 `not_run`이다. 실제 메시지를 고정 모델에 넣어 합성 코드 근거와 업무 답변을 자동으로 생성하지 않는다. 모델 분석을 붙이려면 실제 자료의 처리 목적·제공자·정책과 검증을 별도로 정한다.

### 전송 분리

로컬 보고서 출력과 Slack 메시지 전송을 서로 다른 경로로 둔다. 초기 외부 전송 어댑터는 비활성화하고, 모델·보고서 내용만으로 활성화하지 못하게 한다.

Slack 메시지 전송, 외부 모델 호출, Git 원격 변경은 서로 다른 목적지와 자료를 다루므로 각각 정책을 검사한다. 코드 변경 승인은 어느 전송에도 포괄적인 허가가 아니다.

## 7. 회사 자료와 비밀정보

회사 계정·저장소 연결 전에 AI 제공자, 모델, 실행 위치, 전송 가능 자료, 보관 기간과 감사 요구를 회사 정책에 따라 확인한다. 회사 승인이 없으면 합성 데이터로 계속 개발한다.

- 회사의 소프트웨어 반입 절차를 따른다. 하네스의 범용 코드만 회사 환경으로 가져가고, 회사 코드·설정을 개인 원격 저장소로 보내지 않는다.
- 실제 토큰, 사용자 설정, SQLite, 승인 기록, 원문 메시지, 보고서, 로그와 worktree를 커밋하지 않는다.
- `.env.example`과 fixture에는 명백한 가짜 값만 사용한다. 실제 회사 코드, 비공개 대화와 고객 자료를 합성 fixture로 위장하지 않는다.
- 자격증명은 승인된 비밀 저장소에 두고 필요한 프로세스에만 제공한다. 개인·회사 계정의 자격증명, 캐시와 보고서를 분리한다.
- 모델에는 작업에 필요한 최소 자료만 보낸다. 토큰·키가 입력, 오류 메시지, diff, 보고서와 로그에 포함되지 않도록 검사한다.
- 보고서와 실행 로그도 회사 정보를 포함할 수 있다. 저장 위치·열람 권한·마스킹·보관·삭제 정책을 정한다.
- 단계 2에서는 알려진 비밀 패턴과 지원하는 이메일·전화번호 패턴을 저장 전에 마스킹하고 원문 프레임·blocks·첨부파일을 통째로 저장하지 않는다. 이 패턴 검사는 모든 개인정보를 판별하지 못하므로 실제 회사 자료 처리의 승인 근거로 쓰지 않는다.
- 단계 2 메시지·문맥 payload에는 `retentionHours` 1~168시간, 기본 24시간을 적용하고 수신·조회·정리 시 만료 자료를 제거한다. 이벤트 중복 키, 원본 ID·revision·삭제 marker는 DB 수명 동안 유지하며 본문 만료 뒤 같은 이벤트가 자료를 되살리지 못하게 한다. 최소 metadata는 보관 기한 뒤에도 남으므로 회사 승인 시 이 범위와 DB 폐기 정책을 함께 확인한다.
- SQLite의 논리적 삭제는 백업·파일시스템·디스크의 물리적 완전 삭제를 보장하지 않는다. DB 폐기 후에는 과거 중복·순서 보존도 보장하지 않는다. CLI 출력을 별도 파일로 내보낸 경우에는 사용자가 정한 보관 정책을 적용한다.
- `.gitignore`는 커밋 실수를 줄이는 수단일 뿐 접근 통제나 유출 방지 장치 전체를 대신하지 않는다.

Gmail·Calendar·Drive는 후속 선택 기능이다. 연결된 계정이 있다는 이유로 전체 자료를 읽지 않는다. 읽기 범위와 보내기·일정 변경·파일 수정·공유 권한을 각각 정의한다.

## 8. 취소, 실패와 감사 기록

실행 전 취소는 대기 작업을 종료한다. 실행 중 취소는 새 동작을 막고 실행 중인 프로세스를 종료한 뒤, 이미 바뀐 파일과 남은 영향을 보고한다. 취소가 이미 보낸 메시지나 원격 변경을 되돌린다고 가정하지 않는다.

실패와 재시작 때 작업 상태, 잔여 diff, 승인 사용 기록을 보존한다. 검사별로 `passed`, `failed`, `not_run`과 이유를 남긴다. 재개는 현재 상태와 승인 범위를 확인한 후 결정하며 자동으로 반복 실행하지 않는다.

감사 기록에는 누가 어느 계획을 승인했는지, 어떤 정책 검사를 통과·실패했는지, 무엇을 실행했고 어떤 결과였는지를 남긴다. 원문 대화·코드 전문·비밀값을 무조건 기록하지 않는다.

## 9. 보안 검증의 완료 조건

다음 경계는 실제 실패 테스트로 확인한다.

- 승인 전 대상 파일 변경과 대상 스크립트 실행이 없음.
- 비허용 경로·symlink·비밀 파일이 모델 입력과 로그까지 도달하지 않음.
- 외부 자료의 악성 지시와 잘못된 모델 JSON이 권한 변경·명령 실행을 만들지 못함.
- 만료·취소·위조·중복 승인, 변경된 계획·커밋·요청 revision을 거부함.
- 취소·재시작 후 자동 재실행이 없고 잔여 작업물이 보존됨.
- 별도 허가 없는 메시지 전송·push·PR이 없음.
- 승인 범위 밖 변경과 실패·미실행 검사를 성공으로 보고하지 않음.

단계 3-A의 승인 기록과 아직 구현하지 않은 승인 소비·실행 기능을 구분한다. 실제 격리·patch·대상 검사·실행 취소·복구는 **미구현**이며 항상 거부되는 실행 기본 동작을 검증한다. 후속 단계의 보안 검증을 통과했다고 미리 기록하지 않는다. 상세 수용 테스트는 기준 계획서에서 관리한다.
