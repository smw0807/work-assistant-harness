# 회사 장비의 오프라인 점검·합성 검증 인수인계

2026-11-16 작성. 회사 장비의 새 대화에서 **하네스 자체의 오프라인 점검과 합성 로컬 검증**을 이어가기 위한 문서다. 회사 제품 저장소·업무 자료·실제 인증정보 접근과 실제 모델 호출은 포함하지 않는다. 이 문서를 저장하거나 읽었다는 사실은 회사의 소프트웨어 반입·실행·결과 공유 허가가 아니다.

## 인수인계 작성 당시 상태

| 항목 | 상태 |
| --- | --- |
| 저장소 | `work-assistant-harness` — 조사 대상 회사 제품 저장소와 별개 |
| 구현 기준 커밋 | `370048d10aa8112f5e40135c9e2c7b012a43733b`, `main`에 푸시 완료 |
| 커밋 메시지 | `feat(migration): 회사 이전용 오프라인 점검 추가` |
| 구현 완료 | `migration-check` CLI, 비활성 설정 템플릿, 실행 가이드, 검증 결과 문서 |
| 개인 Mac 검증 | lint·typecheck·빌드 passed. 전체 1,270개 중 1,234 passed, 0 failed, native opt-in 36 skipped |
| 개인 Mac 정적 점검 | 9 passed, 범위 밖 8 not_run, 종료 코드 0 |
| 회사 장비 검증 | 아직 not_run. 개인 장비 결과를 회사 장비 결과로 대신 기록하지 않음 |
| 기존 계약 | relay-v2/v3·개인 수집 v2·실행 예산 v1·민감정보 검사·수집 한도 유지 |

기준 커밋은 개인 장비에서 검증한 구현의 식별자다. 회사에서는 이 인수인계 문서가 추가된 후속 문서 커밋까지 포함한 승인된 사본을 사용하고 현재 HEAD와 변경 사항을 별도로 기록한다. 기준 커밋으로 자동 checkout/reset하거나 기존 변경을 지우지 않는다. 코드가 달라져 있으면 차이를 먼저 검토하고 과거 통과 결과를 그대로 적용하지 않는다.

위 표는 기준 커밋 당시의 기록이다. 후속 구현은 pnpm의 특정 버전 고정을 제거하고 디렉터리 하위 항목 수 변화를 경로 교체와 구분한다. 실제 장비에서 실행한 버전·검사 결과·변경 파일과 미실행 항목은 각 실행의 새 비공개 로컬 기록에 남긴다.

native 파일을 지정하지 않을 때는 [부분 진단 템플릿](../config/migration-check.partial.example.json)의 별도 입력을 사용할 수 있다. 부분 진단은 OS·Node·pnpm·경로·런타임 조건만 확인하며 native와 sandbox 파일 경로에 접근하지 않는다. 부분 통과와 전체 준비 미완료 상태를 구분하고, 기존 전체 진단의 조건이나 전송·수집 계약을 낮추지 않는다.

개인 환경의 비공개 검증 자료는 옮기지 않는다. 회사 실행에 필요한 기준은 저장소의 [4-C-14 검증 결과](stage-4c14-result.md)에 있으며, 그 문서에 연결된 개인 장비의 로컬 자료 경로를 열거나 찾을 필요가 없다. 과거 실제 호출·승인·조사 계획도 이번 인수인계의 실행 대상이 아니다.

## 후속 회사 읽기 전용 준비와의 구분

후속 `company-readonly-*`는 회사용 등록·로컬 보관·검토 대기를 구현한 별도 경로다. 현재는 합성 저장소로만 검증하며 이 문서의 장비 점검 요청으로 실제 회사 자료를 읽지 않는다. 기본 정책은 읽기·보관 모두 `unconfirmed`이고 미확인 상태에서는 등록 파일·대상 metadata 접근도 차단한다. 사용법과 보관 조건은 [README](../README.md#회사-저장소의-오프라인-읽기-전용-준비)를 따른다.

회사 자료의 실제 로컬 읽기·보관, AI 제공자·계정·전송 조건은 별도로 정해야 한다. 기존에 확인한 소프트웨어 반입·합성 테스트·공유 범위를 다시 승인받을 필요는 없다. 준비 자료의 `AWAITING_APPROVAL`과 전송/실행 권한 false는 유지하며 실제 승인·native·모델 호출 명령은 제공하지 않는다. 오프라인 준비 결과가 회사 정책 검증이나 실제 조사 성공을 뜻하지 않는다.

## 회사에서 확인할 조건

후속 [검토용 Git 사본 실험](company-evidence-copy-design.md)은 고정 합성 객체로 같은 commit의 작은 사본을 구성하고 기존 판독기로 검사한다. 실제 회사 사본 생성·추출기나 새 명령은 제공하지 않는다. 큰 pack 때문에 거부되더라도 이 실험을 근거로 한도 상향·원본 repack·회사 Git 명령을 자동 실행하지 않는다. 합성 결과는 [4-C-16 결과](stage-4c16-result.md)를 따른다.

이후 방향은 원본 레포의 직접 읽기이며 사본 생성기 개발은 진행하지 않는다. [회사 Git 선택 읽기 설계](company-git-range-reader-design.md)의 1차 codec·공유 예산·고정 profile/byte proof 기록은 [codec 결과](stage-4c17-codec-result.md)에, 2차 commit/tree·작업 index parser와 위치 지정 읽기·두 pass 재검증은 [reader 결과](stage-4c17-reader-result.md)에 보존한다. 3차는 별도 회사 준비 v2의 정책/등록 gate·안전 발췌·전용 보관·CLI·supervisor를 연결한다. 합성 자료만 사용하며 3차에서 회사 자료·실제 인증·native·실제 모델·외부 서비스에 접근하지 않는다. 실제 검사와 미검증 항목은 [3차 통합 결과](stage-4c17-integration-result.md)에 기록한다.

`company-git-range-source-v1`은 계속 metadata/hash만 반환하는 내부 API다. v2 준비는 별도 `company-readonly-registration-v2`와 고정 `gitProfileHash`를 요구하고 `company-readonly-v2-plan/inspect/cancel/prune` 명령을 사용한다. [README의 v2 사용법](../README.md#구간-판독기를-사용하는-회사-준비-v2)에 정확한 설정·명령을 둔다. 기본 미확인 정책은 등록·대상 접근 전에 거부하고 기존 v1 명령·DB·계약은 자동 전환하지 않는다. 선택 원문은 내부 메모리에서 안전 발췌로 바꾼 뒤 해제하며, 최종 pass에서 원문 hash와 발췌를 다시 확인한다. raw 본문이나 내부 FS 경로를 일반 출력에 내보내지 않고 허용된 로컬 위치에 상세 자료를 보관하며 공유 요약에는 집계만 남긴다.

실제 I/O·할당은 기존 고정 profile 예산을 공유하며 두 pass의 반복 읽기·해제도 계수한다. v2 부모 supervisor는 30초 기한에 `SIGTERM`, 250ms 유예 뒤 `SIGKILL`을 요청하며 child의 `close`만 종료 확인으로 인정한다. 부모 생존·OS 신호 처리에 의존하고 부모 자체가 강제 종료되면 독립 guardian이나 고아 프로세스 방지는 제공하지 않는다. 닫힘 불확정 FD는 계수를 유지하며 같은 번호로 재시도하지 않는다. worker의 V8 old-space 128MiB 설정, 관리 Buffer 계수와 RSS 256MiB 합성 측정 목표는 서로 다르며 OS RSS 강제 상한이 아니다.

소유자 전용 runtime은 `store/`와 `runs/`로 나누며 부모/디렉터리 `0700`, 파일 `0600`을 요구한다. worker는 `store/`만 쓸 수 있다. 시작 전에 ID와 hash를 별도 시작 기록에 fsync하고 결과를 다른 파일에 한 번 기록한다. 저장 후 응답을 잃거나 부모 종료로 결과 파일이 없으면 `unknown`이며 같은 ID의 `inspect`로 보관 상태·hash·기간을 확인한다. 이 조회는 원래 worker의 종료를 증명하지 않으며 자동 재시도하지 않는다. 새 명시적 `plan`만 새 ID를 만든다.

byte proof 단독은 metadata 일관성 검사이며 전체 pack checksum·미조회 객체는 계속 `not_checked`다. 선택 경로 복원에는 비선택·과거 delta base의 부수 읽기가 있을 수 있다. 실제 회사 적용 전 기존 읽기·보관 승인과 추가·미확인 범위만 대조하며 이미 확인한 정책을 다시 묻지 않는다. 기존 진단·회사 v1·수집 한도/hash·의존성은 유지한다. 이번 합성 통합이나 이전 진단 통과는 실제 회사 원본 적용·호환성 성공 또는 새 자료 접근의 허가가 아니다.

새 대화에서 아는 범위만 알려주고, 모르는 항목은 `미확인`으로 둔다. 계정명·토큰·사내 URL·회사 코드·저장소 경로를 이 양식에 넣지 않는다.

```text
회사 소프트웨어 반입: 허용 / 제한 있음 / 미확인
회사 장비의 로컬 개발 테스트: 허용 / 제한 있음 / 미확인
검증 결과의 외부 공유: 허용 범위 / 미확인
```

OS/CPU와 설치된 개발 도구 같은 기술 조건은 허용된 장비에서 직접 확인한다. 이미 확인된 허용 사항을 다시 승인받지 않는다. 반입·테스트 정책이 미확인이면 그 항목만 확인하고 해당 작업은 기다린다. 결과 공유가 미확인이면 원본 로그·설정·장비 경로를 대화나 원격 저장소로 전송하지 않는다.

현재 호스트·런타임 조건은 macOS ARM64, Node `>=26.12.1 <27`이다. pnpm은 회사가 허용한 설치 버전을 사용하며 특정 버전으로 고정하거나 자동 전환하지 않는다. 진단은 정상 pnpm 선언과 관찰 버전을 기록할 뿐 모든 버전의 호환성을 보장하지 않는다. 실제 lint·typecheck·합성 회귀 결과를 별도로 남긴다. 고정 native는 macOS ARM64 Codex `0.154.0`이며 SHA-256은 다음과 같다.

```text
4f85982624b3898c8991cb80c0981b2aa71070e3537046c9a95950318a95afcc
```

소스·lockfile·런타임·개발 의존성과 바이너리는 회사가 승인한 경로로 준비한다. 설치를 위해 외부 npm, 사내 패키지 저장소 또는 오프라인 반입 중 무엇을 사용할 수 있는지 확인한다. 이번 검증 요청으로 자동 다운로드·설치·업그레이드를 시작하지 않는다. 자동 다운로드를 유발하는 미준비 패키지 매니저 실행도 피한다. 미지원 OS/CPU나 누락된 도구는 `blocked`/`not_run`과 이유를 기록하고 별도 준비 또는 이식 계획으로 남긴다.

## 접근·실행 범위

허용 범위는 하네스 상태 확인, 지정된 진단 설정/native의 제한된 읽기, 필요한 경로 메타데이터 확인, 새 비공개 설정·결과 위치 준비와 회사가 허용한 합성 로컬 검증이다. 파일 탐색은 하네스와 이번 작업에서 명시한 새 위치로 한정한다. 바이너리 위치가 없으면 사용자에게 지정받고 홈 디렉터리 전체를 탐색하지 않는다.

- 회사 제품 저장소·업무 문서·실제 로그·고객 자료는 읽지 않는다. 그 저장소의 설치·테스트·빌드·Git 작업도 실행하지 않는다.
- 실제 인증 파일·환경변수의 비밀값·키체인을 읽거나 계정 상태 조회·로그인·refresh를 수행하지 않는다. 환경변수나 사용자 설정 전문을 출력하지 않는다.
- 실제 모델·Slack·외부 업무 서비스를 호출하지 않는다. native Codex와 `sandbox-exec`를 실행하지 않으며 `codex --version`도 실행하지 않는다.
- 개인 인증·캐시·DB·승인·보고서를 복사하거나 기존 승인을 재사용하지 않는다. 실제 호출 계획이나 승인 기록도 만들지 않는다.
- 소스·계약·상한·기준 hash를 변경하거나 회사의 제한을 우회하지 않는다. commit·push·PR과 자동 원격 동기화는 회사 검증 요청에 포함하지 않는다.

`migration-check` 진단 자체는 쓰기·DB 접근·자식 실행·네트워크 통신을 하지 않는다. 반면 `pnpm harness`와 `pnpm test`는 먼저 `dist`를 빌드하고, 합성 회귀는 임시 파일·SQLite·권한 변경·symlink/hardlink·FIFO·Node 자식 프로세스·종료 신호·`127.0.0.1` 모의 HTTP 서버를 사용한다. 이 로컬 테스트 동작의 회사 허용 여부를 확인한다. 테스트가 자체 생성한 가짜 인증 fixture는 실제 인증정보와 구분한다. 제한된 검사를 우회하지 않고 미실행 사유를 기록한다.

## 새 대화에서 수행할 순서

1. 현재 작업 폴더가 하네스인지 확인하고 기존 변경을 보존한다. [AGENTS.md](../AGENTS.md), [구조](architecture.md), [코딩 컨벤션](coding-conventions.md), [보안과 승인](security-and-approval.md), [구현 계획](implementation-plan.md), [이전 가이드](migration-guide.md), [검증 결과](stage-4c14-result.md), [설정 템플릿](../config/migration-check.example.json)을 읽는다. 과거 승인이나 대화의 묵시적 권한을 추정하지 않는다.
2. 회사의 반입·로컬 테스트 허용 범위와 OS/CPU·설치 도구를 확인한다. native 파일을 지정하지 않으면 부분 진단을 선택하고 native·sandbox 파일 검사는 미실행으로 남긴다. 전체 진단의 실제 바이너리는 승인된 지정 경로의 메타데이터·헤더·고정 hash로만 확인한다. 누락·불일치를 설치나 pin 변경으로 해소하지 않는다.
3. 가이드에 따라 하네스·회사 제품 저장소 밖의 새로운 비공개 설정/런타임/결과 위치를 준비한다. `enabled:false`, 디렉터리 `0700`, 설정·결과 파일 `0600`을 유지한다. 기존 파일 덮어쓰기, 기존 디렉터리의 재귀적인 권한 변경과 실제 DB 접근은 하지 않는다.
4. 아래 기존 정적 점검 명령을 실행한다. 예시 경로는 준비한 설정의 절대 경로로 바꾼다. 전체 상태와 종료 코드, 각 항목의 상태를 함께 기록한다. 정상 전체 진단은 9개 통과·범위 밖 8개 미실행이다. 정상 부분 진단은 7개 통과·10개 미실행이고 `partialStatus:passed`여도 `status:blocked`와 종료 코드 1을 유지한다. 남은 native·sandbox 파일 검사는 `remainingChecks`, 필요한 다음 정적 점검은 `nextActions`로 구분한다. 두 모드 모두 `liveReady=false`, `executionAllowed=false`, `approvalCreated=false`를 확인한다. 입력 오류는 JSON 보고서 생성 전에 거부될 수 있다.

```sh
pnpm harness migration-check --config /absolute/path/to/private-migration/migration-check.json
```

5. 지원 환경과 회사 정책이 허용하면 [package.json](../package.json)의 lint·typecheck·합성 회귀를 순차 실행한다. 두 native opt-in 환경변수를 명시적으로 제거한다. 아래 테스트 서브셸의 `umask 022`는 개인 검증 때와 같은 fixture 생성 조건이며 부모 셸의 umask를 바꾸지 않는다. 회사 권한 정책과 충돌하면 완화하지 말고 `not_run`으로 남긴다. 비공개 자료 준비용 `umask 077`을 테스트에 그대로 전파하면 권한 관련 fixture의 판정이 달라질 수 있다.

```sh
pnpm lint
pnpm typecheck
(
  umask 022
  env -u HARNESS_NATIVE_CODEX_PROBE -u HARNESS_NATIVE_CODEX_PATH pnpm test
)
```

위 예시는 결과 파일을 자동 보관하지 않는다. stdout/stderr를 저장할 때는 새 비공개 파일을 `0600`으로 준비하고, 기존 로그를 덮어쓰지 않는다. 테스트 서브셸의 umask와 결과 파일 생성 권한을 구분한다. `pnpm test`에 빌드가 포함되므로 의미 없는 빌드·전체 회귀 반복은 필요하지 않다. 기존 검사 36개가 skip된 개인 결과는 회사에서 관찰할 결과의 참고치이며 결과를 맞추기 위해 검사를 바꾸지 않는다.

6. 회사 장비에서 실제 관찰한 `passed`/`failed`/`not_run`, 종료 코드, 현재 커밋, 계약 보존 여부, 이번 진단 설정과 허용된 파일 메타데이터의 전후 상태, 결과 파일 hash를 새 로컬 자료로 기록한다. 파일 목록 확인과 결과 보관은 준비/검증 작업이며 진단기의 무쓰기 동작과 구분한다. 종료된 검증 프로세스와 임시 자료 정리 여부를 확인하되 하네스가 만든 작업 범위 밖을 탐색하거나 삭제하지 않는다.

최종 답변에는 공유가 허용된 상태·집계와 미검증 범위, 필요한 다음 최소 작업만 남긴다. 회사의 실행·전송 승인이나 실제 격리 동작을 이 정적 점검으로 증명했다고 표현하지 않는다. pnpm 선언은 실행기가 제공한 미검증 메타데이터이고, 권한/hash 확인도 ACL·실제 쓰기 성공·저장 용량·이후 무변경의 보증은 아니다.

## 새 대화에 붙여 넣을 짧은 시작 문구

회사에서 승인된 하네스 프로젝트를 연 뒤 다음 문구를 사용한다. 허용 여부를 알고 있다면 위의 세 줄 양식을 덧붙인다.

```text
현재 work-assistant-harness의 docs/company-offline-handoff.md를 읽고,
회사 장비의 오프라인 점검과 합성 검증을 그 문서의 범위에서 진행해줘.
회사 자료·실제 인증정보 접근과 실제 모델/native 호출은 제외해줘.
기존 계약과 한도를 유지하고, 회사 반입·테스트 정책 중 미확인 사항만 먼저 확인해줘.
결과는 허용된 로컬 위치에 보관하고 공유 가능한 요약만 알려줘.
```
