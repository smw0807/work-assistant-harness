# 단계 4-C-25: 호출부·검사 범위 검토와 합성 격리 진단

2026-11-19. 이전 읽기 준비에서 확인한 수정 후보의 호출부와 검사 설정을 새 제한 읽기로 검토했다. 기존 계약·등록 gate·수집/실행 한도와 하네스 프로덕션 코드를 변경하지 않았다. 회사 코드·경로·업무별 요구사항은 이 문서에 포함하지 않는다.

## 제한 읽기와 실패 구분

최초 선택의 동적 경로 문법은 기존 등록 gate에서 거부했다. 해당 gate를 완화하지 않고 지원 범위로 새 등록을 구성했다. 이후 7파일 준비는 두 번째 pass의 최종 guard에서 metadata8,192회에 추가1회를 요청해 실패했다. 같은 ID 조회는 `NOT_FOUND`였고 원래 실패 작업을 재시도하지 않았다.

호출부와 검사 환경을 별개 목적으로 나눈 준비는 각각 성공했다. 두 작업 모두 같은 ID·계획 hash·본문 보관 기간·`AWAITING_APPROVAL`·worker 종료를 확인했다.

| 목적 | 파일·범위 | 발췌 바이트 | pass | metadata |
| --- | --- | --- | --- | --- |
| 호출부 | 3·3 | 9,498B | 2 complete | 6,512/8,192 |
| 검사 설정·예제 | 4·5 | 21,977B | 2 complete | 6,514/8,192 |

각 준비의 관리 메모리 최고는5,914,864B였다. 작업 파일 preflight의 전체 view 바이트와 위 발췌 바이트는 끝 빈 줄 처리 때문에 다르다. 최초 실패와 독립된 목적별 성공을 구분하며, 큰 선택이 한도 내에서 성공한다고 주장하지 않는다.

새로 발견한 실제 검사 bootstrap1파일은 별도 준비에서 `COMPANY_GIT_RANGE_INVALID_SOURCE`·`object_lookup`으로 실패했다. 같은 ID 조회는 `NOT_FOUND`다. 객체 부재를 확정하거나 추가 복구하지 않았으며 그 본문을 검증된 근거로 사용하지 않았다.

## 검사 환경과 변경 제안

기본 검사 설정은 특정 unit project만 선택해도 최상위 설정을 읽으며 프레임워크 초기화를 수행할 수 있다. 따라서 환경 파일 읽기·기존 bootstrap·자동 생성 선언·일반 캐시를 피하는 별도 설정과 mock이 필요하다. 로컬 Vite 타입에서 `envDir:false` 지원을 확인했다. 이 설정만으로 OS 격리가 제공되지는 않는다.

호출부의 기존 기본 동작을 유지하는 opt-in 수정4파일, 신규 검사3파일과 수용 조건15개를 비공개 제안에 기록했다. 원본 레포에서 새 브랜치를 사용하는 방식이며 전체 레포 사본은 만들지 않았다. 검사에 필요한 최소 파일과 공개 의존성만 담는 별도 검사 입력은 아직 구성·실행하지 않았다.

현재 pnpm12.16.1을 사용했고 자동 버전 전환·설치·lockfile 변경은 하지 않았다. 설치된 제품 런타임과 선언된 의존성의 일부 차이도 남아 있다. 실제 검사 전에 전용 설정·모듈 해석·Linux용 의존성·읽기/쓰기 목록과 기존 자원 한도를 확인해야 한다. 충족하지 않으면 자동 설치나 한도 상향 없이 미실행 사유를 기록한다.

## 실제 장비의 합성 Docker 진단

실제 사용자 인증 설정 대신 전용 빈 설정을 사용해 로컬 Engine·이미지만 조회했다. 이전 환경의 이미지는 없었고, 이미 로컬에 있는 `node:24.22.2-bookworm-slim`의 전체 이미지 ID와 Engine28.3.3을 비공개 설정에 고정했다. 이미지 다운로드·빌드와 회사 파일 마운트는 하지 않았다.

기존 `pnpm harness sandbox-check --config <private-json> --data-dir <private-directory>`를 실행했다. 기존 Docker 정책의 메모리128MiB·swap 금지·PID64·CPU0.5·출력16KiB 및 각 probe 시간 한도를 유지했다.

| 항목 | 결과 |
| --- | --- |
| 고정 probe | passed — boundary, pids, memory, timeout, output 5개 |
| 전체 확인 항목 | passed — preflight·자식 종료·양성 대조·보호 canary 포함9개 |
| 생성 container | passed — 5개 모두 종료·제거 |
| 보호 canary | passed — 전후 hash 일치 |
| 회사 원본/Git 메타데이터 | passed — 관찰18개 전후 일치 |
| 하네스 보존 | passed — 결과 문서 작성 전569파일 hash 일치 |
| 회사 코드 수정·브랜치 생성·제품 검사/설치/빌드 | not_run |
| 실제 제품 검사 workload의 격리·의존성 | not_run |
| 실제 인증·native Codex·모델·외부 서비스 | not_run |
| 전체 하네스 회귀 재실행 | not_run — 프로덕션 코드 변경 없음; 직전 전체 결과는 [4-C-23](stage-4c23-result.md) |

합성 진단에는 기존 하네스 스크립트의 컴파일이 포함된다. 성공해도 `executionEnabled:false`이며 회사 실행 승인이나 범용 제품 검사 실행기가 추가된 것은 아니다. 원본 관찰은 선택 파일의 메타데이터 비교이고 전체 저장소 내용의 원자적 snapshot이나 전체 clean 판정이 아니다.

## 로컬 보관과 다음 작업

소유자 전용 자료는 `/private/tmp/harness-company-feature-scope-mkmy6690`에 보관했다. 상세 수정 제안은 가장 이른 근거 기한인 2026-11-19 09:06:33.982Z까지, 새 호출부·검사 근거는 각각09:20:25.736Z·09:20:45.558Z까지다. 이번 통합 감사 기록은2026-11-20 08:18:54.346Z까지이며 각 준비의 기존 감사 기한도 유지한다. 명시적 prune·파일 정리가 필요하고 백그라운드 삭제를 보장하지 않는다.

다음은 구체적인 파일 범위에 대한 제품 변경 승인 후 원본 레포의 새 브랜치에서 구현하는 작업이다. 이미 확인한 회사 반입·로컬 보관 정책을 다시 묻지 않는다. 새 회사 검사 실행은 유효한 소유자 승인과 정확한 검사 환경 검증을 모두 만족한 뒤 진행한다. 현재 읽기 준비 상태나 이전 Git 객체1개 복구 승인을 제품 수정 권한으로 사용하지 않는다.
