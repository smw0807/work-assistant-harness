## 현재 근거와 구현 범위

이전 본문의 보관 기한이 지나 현재 원본을 새 v3 준비3건으로 검증했다. 호출부3파일, 관련 구현2파일, 검사 설정2파일을 각각 두 pass로 확인했고 기존 수집 계약·hash·한도를 유지했다. 입력 파일 이름을 잘못 지정한 첫 호출은 준비 작업 생성 전에 거부됐으며, 이름을 바로잡은 뒤 새 준비를 수행했다.

기존 기본 호출 동작을 유지하는 opt-in 경로와 필요한 두 호출부의 연결을 작성했다. 중복 완료, 관측 이벤트 지연, 오래된 callback, 문서 비가시 상태, DOM 교체와 콘텐츠 교체를 검증한다. 구체적인 코드·파일 이름·업무 조건·patch는 비공개 위치에만 보관했다.

이 입력은 기존 합성 실행기의 `64KiB/16파일` 고정 workspace 계약에 해당하지 않는다. 해당 계약과 ExecutionPort는 변경하지 않고, 별도 검토한 일회용 controller에서 승인된 소스/검사와 공개 의존성을 구분해 검증했다. 현재 pnpm12.16.1은 하네스 준비·정리에 사용했다. 컨테이너에서는 확인한 제품 unit script의 Vitest 인자를 고정해 Node로 실행했으며 다른 pnpm을 설치하지 않았다.

## 현재 브랜치 확인과 원본 적용

검토 중 기준 commit이 한 번 더 바뀌어 실행 전 확인이 거부된 경우에는 회사 코드나 container를 실행하지 않았다. 수정 대상3파일 hash가 같음을 확인한 뒤, 현재 checkout과 독립된 승인 스냅샷을 격리 검사했다. 이후 실제 적용 직전에 체크아웃 브랜치도 달라져 적용을 보류하고 기준을 확인했다.

사용자가 현재 브랜치를 기준으로 적용을 허용한 뒤 새 v3 준비로 최신 commit과 기존 수정 대상3파일을 다시 확인했다. 첫 적용 호출은 검토 입력의 notice에 없는 원본 hash를 비교해 writer 시작 전에 거부됐다. 원본 hash를 보관하는 `collected.sourceViews`로 비교 위치를 바로잡고3개 증명의 일치를 확인한 뒤 실제 writer를 실행했다. 검증을 생략하거나 원래 오류를 성공으로 처리하지 않았다.

별도 신뢰 controller는 계획·writer·검사 결과·7파일 hash를 고정하고 HEAD/index/현재 ref/packed refs/새 ref의 잠금을 독점 확보했다. 기존 원본을 다시 확인한 뒤 새 ref를 덮어쓰기 없이 공개하고, 파일별 내용을 fsync·교체·검증한 다음 HEAD를 마지막에 전환했다. 기존 파일의 mode를 유지하고 HEAD 전후7파일을 다시 확인했다. 자신의 inode에 해당하는 임시 파일과 잠금만 정리했다. Git CLI·설정·hooks·인증에는 접근하지 않았다.

합성15개는 정상 적용·기존 권한 보존, 네 종류의 기존 잠금, dirty 원본, loose/packed ref 충돌, symlink, 기존 새 경로, fsync 실패, 동시 편집, HEAD 전환 뒤 다른 프로세스의 잠금 보존, 새 파일 공개 후 정리 실패, 부분 감사 쓰기를 검증했다. 실제 작업은 파일·ref·HEAD를 아우르는 단일 원자 트랜잭션이 아니며, Git 잠금이 일반 편집기를 막지는 않는다. 오류 시 부분 적용을 기록하고 자동 rollback하지 않는다. 이 writer는 승인된7파일용 고정 작업이며 하네스의 일반 회사 실행 명령을 추가한 것이 아니다.

적용 후 독립 확인에서7파일이 검증한 초안과 같고, 새 브랜치가 승인한 기준 commit을 가리키며, 원래 ref·index와 기존 파일 mode가 보존되고 자신의 잠금·임시 파일이 없음을 확인했다. 전체 저장소 clean이나 다른 외부 작업의 무변경은 주장하지 않는다. 다음 최소 확인은 사용자 환경에서의 실제 브라우저 동작 검토다. 전체 제품 lint/typecheck/build와 실제 API를 사용하는 검증은 아직 수행하지 않았다.
