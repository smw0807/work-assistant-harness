# 단계 4-C-16: 검토용 Git 사본의 설계·합성 검증

2026-11-16. 기존 회사 판독기의 계약과 한도를 유지하면서 같은 기준 commit의 선택 경로를 작은 사본으로 검증할 수 있는지 합성 자료로 확인했다. 범위와 수용 조건은 [사본 설계](#당시-사본-설계)를 따른다. 실제 회사 원본이나 외부 서비스에는 접근하지 않았다.

## 변경 범위

- 고정 합성 저장소와 사본을 생성하는 test-only fixture 및 기존 회사 판독기를 사용하는 테스트 6개를 추가했다.
- README·구조·보안·구현 계획·인수인계에 사본의 출처·원문/metadata 보관·보증 범위와 미구현 기능을 기록했다.
- 운영 코드·계약·한도·설정 예제·의존성·lockfile은 변경하지 않았다. 새 CLI·실제 exporter·회사 자료 추출 기능은 없다.

## 합성 사본에서 확인한 결과

| 사례 | 확인 결과 |
| --- | --- |
| 유효한 과대 객체 수 pack | 비-delta 객체 4,117개의 pack/index를 생성하고 전체 OID 집합과 checksum을 확인했다. 8MiB 미만이어도 기존 객체 수 상한 4,096개에서 원본 조회가 거부된다. |
| 같은 commit의 작은 사본 | 원본 commit 1개·전체 ancestor tree 6개·선택 blob 6개의 13객체와 선택 작업 파일/index 6개, detached HEAD로 기존 inspect/collect/guard와 준비 payload 검증을 통과했다. |
| 누락·변조 | 필요한 commit/tree/blob 누락, 유효 압축이지만 내용이 바뀐 객체, 선택 작업 파일/index/HEAD 불일치를 거부했다. |
| 생략과 metadata | 비선택 blob·하위 tree·부모 이력은 사본에 없다. 원본 ancestor tree의 비선택 형제 이름은 유지되고 선택 범위 밖 조회는 거부된다. |
| 출처와 이후 변경 | 원본/사본의 sourceRoot·등록/identity hash가 분리된다. 사본 guard는 원본의 이후 변경을 감지하지 않으며 사본의 이후 변경은 거부한다. |
| 정상 관찰 전후 | 정상 준비/조회 전후 합성 원본·사본 파일/Git hash와 metadata가 동일하다. 공격 테스트가 의도적으로 변경한 합성 자료와 구분한다. |

독립 코드/문서 검토에서 수정이 필요한 결함은 발견되지 않았다. 고정 비-delta pack·일반 파일 합성 사례의 결과이며 실제 추출기나 모든 Git 형태의 안전성을 증명하지 않는다. 기존 전체 회귀의 다른 Git 검증과 이번 실험의 범위를 구분한다.

## 검증

설치된 pnpm 12.16.1과 Node 26.12.1을 사용했으며 실제 인증 환경과 native opt-in을 상속하지 않았다. 버전 전환·설치·다운로드는 수행하지 않았다. 실행 로그와 hash는 허용된 비공개 로컬 위치에 보관한다.

| 검사 | 결과 |
| --- | --- |
| lint·typecheck·빌드 | passed — 빌드는 집중/전체 검사에 포함 |
| 회사 집중 검사 | 46 passed, 0 failed, 0 skipped — 신규 6개 포함 |
| 기존 전체 회귀 | 1,304 passed, 0 failed, 36 skipped, 총 1,340 |
| 운영 코드·계약·의존성 보존 | passed — 운영 소스·설정·의존성 223파일 hash 동일 |
| 검증 중 소스 보존 | passed — 소스·테스트·설정 352파일 hash 동일 |
| 문서의 로컬 파일 링크·diff 공백 검사 | passed |
| 실제 회사 자료·인증·native·모델·외부 서비스 | not_run — 이번 범위에서 제외 |

36개 skip은 명시적 native 실행 opt-in을 요구하는 기존 검사다. 전체 합성 회귀에는 허용된 loopback 모의 서버와 Node 자식 프로세스가 포함되며 실제 외부 서비스 연결과 구분한다. 새 사본 fixture는 종료 후 제거됐고 전용 테스트 임시 위치에는 Node compile cache만 남았다. 로그·실행 인자·보존 검사와 집계는 소유자 전용 로컬 결과로 남겼다.

## 남은 범위

합성 fixture가 자체 생성한 Git 객체로 사본을 구성하는 것과 실제 대형 pack에서 필요한 자료를 추출하는 것은 다른 작업이다. 현재 회사 원본 조회의 호환성 문제가 해결됐다고 표시하지 않는다. 실제 exporter와 추출 시 접근/자원 범위, 원문 사본의 보관·정리, 신뢰할 기준 commit과 출처 확인 방식은 미구현이다.

검증된 사본도 선택 경로의 commit 일치와 사본의 무변경만 보증한다. 원본의 이후 상태·전체 이력·서명/작성자 진위는 보증하지 않는다. commit/tree metadata와 선택 원문이 남으며 company runtime DB의 TTL/prune은 사본을 삭제하지 않는다.

이후 사용자는 원본 레포를 직접 조사하는 흐름을 선택했다. 이 검증 기록과 테스트는 보존하되 사본 공급/생성기 개발은 진행하지 않는다. 다음 최소 작업은 [회사 Git 선택 읽기 설계](../design/company-git-range-reader-design.md)에 따른 새 판독기 규칙·자원 후보를 구현하고 합성 자료로 검증하는 것이다. 이 단계의 기존 통과 수를 새 판독기의 검증 결과로 사용하지 않는다.

## 당시 사본 설계

이 절은 폐기한 사본 생성 방향의 설계 근거를 보존한다. 진행 중인 개발 계획이나 실제 회사 자료 추출 기능이 아니다. 기존 독립 설계 문서의 내용을 아래에 통합했다.

**후속 방향 변경(2026-11-16):** 사용자는 원본 레포를 직접 조사하고 수정 시 작업 브랜치를 사용하는 흐름을 선택했다. 이 문서는 완료한 합성 실험 기록으로 보존하며 사본 생성기 개발은 진행하지 않는다. 현재 후속 설계는 [회사 Git 선택 읽기](../design/company-git-range-reader-design.md)다.

이 문서는 선택한 파일이 기준 커밋에 속하는지 기존 판독기로 확인할 수 있는 작은 사본의 설계다. 구현 범위는 `tests/company-readonly-evidence-copy-fixture.ts`와 합성 테스트다. 실제 저장소를 읽어 사본을 만드는 exporter, 사본 전용 새 CLI, 회사 자료 추출 기능은 제공하지 않는다. 기존 `company-readonly-*` 계약·판독기·한도·승인 상태는 변경하지 않는다.

### 목적과 데이터 흐름

선택한 파일이 작아도 Git 객체가 큰 pack에 들어 있으면 현재 판독기가 거부할 수 있다. 이는 선택한 소스의 크기 제한과 별개인 Git 저장 형식 제한이다. 파일당 8MiB, 누적 읽기 64MiB, 객체당 1MiB, pack/index당 객체 4,096개 등의 제한을 높이거나 검사하지 않은 채 건너뛰지 않는다.

이번 실험은 다음 흐름만 검증한다.

```text
테스트가 만든 고정 합성 파일·Git 객체
  ├─ 객체 수 한도를 넘는 합성 pack → 기존 판독기가 거부
  └─ 같은 커밋·선택 경로의 원본 tree·선택 blob으로 작은 사본 구성
       → 기존 회사 판독기 inspect / collect / assertUnchanged
       → 합성 검토 자료와 변조·누락 거부 확인
```

fixture는 자신이 생성한 객체를 이용한다. 큰 pack에서 회사 자료를 추출하거나, 실패한 원본 조회를 다른 도구로 다시 시도하는 기능이 아니다. 합성 사본 통과는 실제 대형 저장소에서 사본을 안전하게 생성할 수 있다는 증명이 아니다.

### 사본에 필요한 자료

| 항목 | 보존 조건 |
| --- | --- |
| 기준 commit 객체 | 원래 바이트와 OID를 유지한다. 파일을 복사하고 새 commit을 만들지 않는다. |
| 경로를 연결하는 tree 객체 | commit의 root tree부터 선택 파일까지 필요한 원본 tree 전체를 유지한다. 비선택 항목을 tree에서 지우면 OID가 달라진다. |
| 선택 blob과 작업 파일 | 원본 객체의 바이트·OID와 작업 파일 내용·실행 비트가 일치해야 한다. |
| HEAD | 같은 기준 commit을 가리킨다. 실험에서는 detached HEAD를 사용한다. |
| index | 선택 파일의 경로·mode·blob OID가 기준 commit과 일치해야 한다. 사본에서 새로 구성한 index이며 원본 index의 복제·증명으로 표시하지 않는다. |
| 생략하는 자료 | 선택하지 않은 blob·하위 tree·부모 commit 이력과 설정·hooks·원격·인증 파일은 수집 대상에 포함하지 않는다. 필요한 경로의 원본 tree 자체는 생략하지 않는다. |

모든 필요한 객체가 기존 한도 안에 있어야 한다. 원본 tree가 너무 크거나 필요한 객체 수·누적 읽기량이 상한을 넘으면 사본도 거부된다. tree를 편집해 상한에 맞추거나 한도를 파일 조각마다 다시 적용하지 않는다. 이 사본은 선택 경로의 증거를 담는 불완전한 객체 저장소이며 일반 개발·checkout·전체 이력 검사용 clone을 보장하지 않는다.

소스 64KiB, 전체 안전 view 64KiB, 발췌 32KiB, 근거 합계 64KiB, 입력 128KiB와 파일 8개·범위 16개·범위당 200줄 등 수집 v2 제한도 그대로 적용한다. Git 파일 256개·읽기 횟수 2,048회 등 기존 판독기의 다른 제한 역시 유지한다. 숫자를 복제한 새 운영 정책을 만들지 않으며 실제 판정은 기존 코드가 담당한다.

### 검증으로 알 수 있는 것과 없는 것

- 등록한 commit OID에서 tree와 선택 blob으로 이어지는 내용 일치, 선택 작업 파일과 index의 일치, **사본**의 관찰된 파일·Git identity 무변경을 검증한다.
- `sourceRoot`는 사본 경로다. 원본 경로를 사본인 것처럼 바꿔 넣거나 원본의 기존 계획·승인·identity hash를 재사용하지 않는다. 사본을 조사한다면 별도 등록과 새 계획이 필요하다.
- 사본을 받은 뒤 원본 작업 파일·HEAD·index가 바뀌어도 사본 guard는 이를 감지하지 않는다. 원본 현재 상태나 전체 clean 상태를 보증하지 않는다.
- OID 검증은 내용 일치를 확인한다. 제공자가 제시한 commit이 승인된 회사 기준 commit이라는 사실, 작성자 신원·서명·원격 저장소의 진위까지 인증하지 않는다. 실제 사용 시 기준 commit과 출처를 어떻게 확정했는지 별도로 기록해야 한다.
- 생략한 이력·다른 파일의 내용과 전체 호출 관계는 알 수 없다. 선택한 파일의 분석과 실제 실행·모델 조사 성공을 구분한다.

### 원문·metadata의 보관 경계

사본에는 안전 view 생성 전의 선택 blob과 작업 파일 원문이 저장된다. commit 본문에는 작성자·이메일·메시지·부모 OID 등이, 원본 tree에는 비선택 형제 파일의 이름·mode·OID 등이 포함될 수 있다. 인증 파일을 제외해도 선택 blob·commit 본문에 내장된 민감값까지 제거됐다는 뜻은 아니다. 이를 마스킹하면 OID가 바뀌므로 원문 없는 안전 발췌 사본이라고 부르지 않는다. 실제 사본에는 별도로 확정한 읽기·보관 범위가 적용되며, 확인된 기존 허용 사항은 다시 묻지 않고 새로 포함되는 자료나 미확인 조건만 확인한다.

실제 사본은 하네스·원본·runtime DB와 분리된 소유자 전용 위치와 보관/정리 기준이 필요하다. `company-readonly-prune`은 runtime DB의 payload·감사 기록만 정리하며 사본이나 원본 Git 파일은 삭제하지 않는다. 기존 payload TTL을 사본의 자동 삭제 보장으로 설명하지 않는다. 이번에는 합성 임시 사본만 테스트 종료 때 정리하며 실제 자료의 보관 작업은 없다.

### 합성 검증 수용 조건

1. 임의 회사 경로나 exporter 입력 없이 테스트가 생성한 고정 합성 저장소만 사용한다.
2. 유효한 pack/index의 객체 수가 4,096개를 초과하는 합성 원본은 기존 판독기에서 거부된다. 같은 commit OID의 작은 사본은 기존 inspect/collect/guard로 검증한다.
3. 선택 경로에 필요한 원본 commit/tree/blob이 누락되거나 변조되면 거부한다. 작업 파일·index 불일치와 사본 생성 이후 변경도 거부한다.
4. 사본의 범위는 선택 경로로 제한하고 비선택 blob/이력은 포함하지 않는다. 포함되는 원본 tree metadata와 사본에 대한 보증 범위를 구분한다.
5. 정상 조회의 전후 합성 원본·사본을 비교한다. 사본 guard가 원본의 이후 변경을 감지한다고 잘못 주장하지 않도록 한계를 테스트한다.
6. 기존 정책·수집 profile·hash·한도·의존성·lockfile을 변경하지 않는다. 기존 `pnpm test:company`, lint·typecheck와 필요한 회귀로 검증한다.

실제 결과와 미검증 범위는 [4-C-16 결과](stage-4c16-result.md)에 기록한다. 새 명령이나 실제 사본 생성 방법을 제공한 것으로 해석하지 않는다.

### 당시 검토했던 후속 범위 — 현재 진행하지 않음

실제 추출기를 만들기 전에 **사본 공급 방식**을 구체화한다. 확정한 기준 commit·선택 경로와 함께 원문/tree metadata 범위, 추출기가 읽을 큰 pack의 범위·자원 예산, 사본의 보관·삭제, 생성 실패 시 정리와 출처 확인 방법이 검토 가능해야 한다. 현재 판독기의 한도를 별도 추출기에 숨겨서 우회하거나 기존 합성 테스트 권한을 실제 추출 권한으로 확대하지 않는다.

큰 pack의 부분 읽기는 개별 파일 크기·객체 수·전체 pack 검증 계약의 의미를 바꾼다. 단순 한도 상향, 일반 shallow clone, 원본 repack을 이번 설계의 자동 해결책으로 사용하지 않는다. 실제 사본 생성은 구현·검증·범위 결정이 남아 있다.
