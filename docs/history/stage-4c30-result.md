# 단계 4-C-30: 회사 수정안의 계획·로컬 검토·승인 기록

2026-11-20. 회사 수정 실행기의 첫 묶음으로 입력한 다중 파일 수정안을 계획·보관·검토·승인하는 경로를 추가했다. 실제 저장소 관찰, 브랜치 생성, 파일 적용과 제품 검사는 연결하지 않았다. 이번 구현과 검증은 하네스 및 합성 자료만 사용하며 회사 자료·실제 인증정보·native Codex·모델·외부 서비스에 접근하지 않는다.

## 구현 범위

`company-change-draft-v1`의 입력은 레포 ID·정수 요청 revision·목적·기준 브랜치/commit/index hash·작업 유형·새 브랜치·파일별 `replace/create`와 새 본문을 담는다. 기존 파일은 변경 전 hash를 선언하고 신규 파일은 `beforeHash:null`로 명시한다. 이 값을 실제 원본 관찰 결과로 취급하지 않고 파일 경로 문자열을 따라가거나 내용을 실행하지 않는다.

새 `company-change-review-v1` 계획은 전체 입력 hash·소유자·원래 기한·정책 한도를 결합한다. 계획과 승인 metadata에는 본문을 복제하지 않고 실제 제안은 별도 만료 payload에 보관한다. `sourceVerification:not_run`, `approvalScope:review-only`, `executionAllowed:false`, `transmissionAllowed:false`를 고정하며 일반 회사 수정 승인으로 자동 승격하지 않는다.

순수 정책·도메인과 저장 포트, 전용 SQLite 어댑터, 준비 서비스와 Nest application context worker를 추가했다. `company-change-plan/review/approve/inspect/cancel/prune` 여섯 명령을 제공한다. `apply/run`, 승인 소비, Git 명령, 모델 호출과 제품 실행 포트는 없다. 새 CLI는 기존 명령 분기와 도움말에만 연결했고 기존 합성·회사 읽기·relay 계약을 변경하지 않았다.

## 입력·승인과 보관

- 최대 8파일, 파일별 새 본문 64KiB, 합계 128KiB, 입력 JSON 256KiB, 계획 JSON 16KiB, 검토 JSON 288KiB로 제한한다. 이 값은 새 검토 계약의 한도이며 실제 파일 쓰기 예산이 아니다.
- 정확한 JSON 키·중복 키·잘못된 UTF-8·비밀 패턴·경로 탈출·Git/비밀 경로·중복 및 대소문자/상하위 경로 충돌·변경 없는 교체를 검사한다. 첫 버전의 경로는 제한된 ASCII 상대 경로만 받는다.
- 승인은 현재 OS 소유자와 정확한 계획 hash, 필수 정수 1~60분에 묶는다. 요청한 전체 기한이 계획의 본문 기한을 넘으면 거부한다. 동일한 활성 승인 재요청은 원래 기록을 반환하고 기한을 늘리지 않는다.
- 만료된 승인은 폐기 상태를 남기고 같은 작업의 재승인을 거부한다. 새 검토에는 새 계획이 필요하며 이전 계획의 기간과 이력을 변경하지 않는다. `usedAt:null`은 항상 유지한다.
- 새 계획의 본문·관리 검토 사본은 생성 후 24시간, 감사 record는 30일이다. 본문·경로 없는 작업 ID hash·계획 hash와 무결성 hash의 최소 중복 표식은 DB 수명 동안 남긴다. 마지막 관찰 시각을 저장해 재시작 뒤의 시각 역행도 거부한다.
- 저장소를 열거나 정리할 때는 본문 열을 조회·측정·hash·JSON 해석하지 않는다. 유효한 본문 조회·검토·승인 시에만 크기·내용·계획 hash를 검증한다. 만료 또는 취소된 본문은 다시 읽지 않고 삭제한다.

로컬 검토 파일은 전체 교체 내용과 변경 전후 hash를 보여 준다. 실제 기존 원문을 읽지 않으므로 제품 파일과의 diff나 최신성 확인 결과가 아니다. 사용자 입력 JSON은 자동 삭제하지 않으며 보관 책임이 남는다. SQLite 논리 삭제와 파일 unlink는 백업·저장장치의 물리적 완전 삭제를 뜻하지 않는다.

## 파일·프로세스 경계

runtime은 private `0700` 디렉터리, DB·검토 파일은 `0600` 일반 파일이어야 한다. 외래 DB는 쓰기 연결 전 읽기 전용 schema 검사로 거부하고 schema·위치·OS 소유자·record hash·파일/sidecar identity를 확인한다. 작업·승인 원장은 SQLite 트랜잭션으로 관리하며 기존 DB와 공유하지 않는다.

CLI 부모는 입력과 runtime의 전체 조상 metadata를 전후 검사한다. 제한 worker는 명시한 입력 파일·runtime·하네스 실행 코드와 의존성만 읽고 store/reviews에만 쓴다. 최소 환경과 V8 old-space 128MiB를 사용하며 네트워크·추가 child/worker·native addon을 허용하지 않는다. 부모는 출력 합계 16KiB와 30초 기한, 종료 요청 후 250ms 유예를 두고 child의 close를 확인한 경우만 성공을 수용한다. OS RSS 강제 상한이나 부모 강제 종료 뒤 독립 guardian 보증은 아니다.

Node의 제한된 읽기 권한에서 루트까지 metadata를 볼 수 없으므로 store는 canonical private 부모와 파일 identity를 검사하고 전체 조상 검사는 CLI 부모가 담당한다. store 단독의 상위 조상 identity 검사 범위는 기존 v3 store와 다르며 기존 v3의 구현은 유지했다. 동일 OS 사용자의 일시적인 경합 전체를 원자적으로 차단한다고 주장하지 않는다.

CLI의 검토 사본 생성과 취소/정리는 runtime별 SQLite lease로 직렬화한다. 검토 사본은 재생성 가능한 자료이며 승인 원장이 아니다. 본문을 쓰기 전에 소유 identity·예상 hash/크기·기한을 metadata로 기록해 중간 쓰기 실패의 만료 정리에 사용한다. 만료 정리에서는 본문을 다시 열지 않는다. identity가 교체된 파일·잘못된 manifest·소유를 확인할 수 없는 고아 파일은 임의로 삭제하지 않으며 성공으로 처리하지 않는다. 소유 inode가 그대로인 관리 사본은 부분 작성되거나 내용이 변경됐더라도 취소/만료 시 삭제될 수 있다. 사용자 입력 원본은 이 정리 대상이 아니다.

검토 디렉터리는 본문/manifest 합계 256파일까지 허용하며 새 사본 한 쌍을 만들기 전에 여유를 확인한다. lease를 다른 프로세스가 보유하면 `BUSY`로 거부하고 자동 재시도하지 않는다. 검토 사본은 전원 장애 내구성을 보증하지 않는다. manifest 작성 전 중단으로 생긴 빈 고아 파일, lease 최초 생성 중단이나 변조로 생긴 불확정 자료는 수동 확인 대상으로 남을 수 있다.

신규 검사는 입력·계획·승인 변조, owner/TTL 경계, 중복/만료 승인, 재시작·시각 역행, 실패 rollback, 여러 연결의 writer 잠금, 외래/복사 DB·파일 교체·링크·권한, 실제 프로세스 간 CLI lease, 본문 없는 출력과 명령 거부를 포함한다. 첫 집중 검사는 CLI 4개가 `COMPANY_CHANGE_UNSAFE_WORKER`로 실패했다. macOS가 자동으로 추가하는 `__CF_USER_TEXT_ENCODING` 메타데이터 키를 엄격한 환경 검사에서 거부한 것이 원인이었다. 이 키만 허용하고 값은 출력하지 않았으며, 부모가 전달하는 환경과 파일/네트워크/하위 프로세스 권한은 넓히지 않았다. 수정 후 집중 검사와 최종 전체 회귀가 통과했고 첫 실패 로그도 보존했다.

이번 작업의 변경은 기존 5파일과 신규 16파일, 총 21파일이다. 검증 로그·기준 hash·보존 감사와 완료 집계는 소유자 전용 `/private/tmp/harness-company-change-review-u82wyul3`에 보관한다. 이 자료에는 실제 회사 본문이나 인증정보가 없으며 합성 검증 증거다. 위 구현·검증 결과는 하네스 변경을 커밋하기 전에 기록했으며 push는 수행하지 않았다.
