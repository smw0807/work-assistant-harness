# 단계 4-C-15: 회사 읽기 전용 준비의 합성 검증

2026-11-16. 회사 저장소의 로컬 검토 자료를 준비하는 하네스 기능을 구현하고 합성 저장소로 검증했다. 실제 회사 자료·인증정보·native Codex·모델·외부 서비스를 사용하지 않았다. 회사의 정책 승인이나 실제 조사 성공을 의미하지 않는다.

## 구현과 경계

- 회사용 정책·등록·준비 계획과 `company-readonly-plan/inspect/cancel/prune`을 추가했다. 기본 정책은 읽기·보관 미확인으로 차단되며 등록 파일과 대상 metadata 접근 전에 정책을 확인한다.
- 기존 수집 v2 reader·민감 검사·안전 view·원본/Git guard를 내부적으로 재사용한다. 기존 개인·relay·수집·실행 예산 계약과 한도, 의존성 버전·lockfile은 변경하지 않았다. 새 검증 스크립트는 `pnpm test:company`다.
- 별도 `company-readonly.sqlite`에 기한이 있는 private payload와 hash 기반 계획을 저장한다. 출력은 상태·식별자·hash·기한뿐이다. 같은 준비의 중복 요청은 취소·만료를 되돌리지 않으며 재시작·취소·만료·보관 정리를 지원한다.
- DB는 소유자·권한·링크·고정 schema와 최초 위치를 검증한다. 외래 DB나 다른 위치로 옮긴 DB는 쓰기 연결 전에 거부한다. 원본 전체·비밀 매치·전체 view는 저장하지 않는다.
- 결과는 `AWAITING_APPROVAL`과 승인 생성·전송·실행 권한 false다. 회사용 승인/실행 명령·인증·전송 포트는 없으며 후속 실제 조사에는 새로운 전송 계약과 승인 계획이 필요하다.

## 최종 검증

설치된 pnpm 12.16.1과 Node 26.12.1을 사용했다. pnpm 버전 전환·설치·다운로드는 하지 않았고 실제 인증 환경과 native opt-in을 상속하지 않았다. 원본 로그·실행 인자·hash는 허용된 비공개 로컬 위치에 보관했다.

36개 skip은 명시적 native macOS 실행 opt-in이 필요한 기존 검사다. 회사 준비 기능의 정책 미확인 시 접근0, 등록/해시/한도 변조, source/Git 무변경, 링크·dirty·동일 view의 원본 변경, 중복·재시작·취소·만료, DB 손상·위치 이동을 합성 자료로 검증했다. 독립 검토에서 지적한 worker 입력/하네스 경로 검증과 DB 위치 보호를 반영한 뒤 최종 검사를 통과했다.

## 남은 범위

정책의 `confirmed`는 운영자의 선언이며 하네스가 회사 승인을 인증한 결과가 아니다. 회사에서 실제로 허용된 읽기/보관 범위와 기간을 확인해야 한다. 현재 저장소 형식·파일/줄 한도와 macOS 환경에 대한 제한은 기존 수집기를 따른다.

Node worker는 전용 데이터 밖 쓰기·추가 프로세스·네트워크를 차단한다. 모든 부모 경로의 metadata 재검증을 유지하려고 파일 읽기 권한은 전체로 열고 실제 경로·파일·바이트 접근은 수집기 코드로 제한한다. 읽기 OS 격리·악성 코드 실행 격리를 보증하지 않는다. 보관 정리는 명령 호출 시의 논리적 삭제이며 자동 daemon·디스크/백업의 물리적 완전 삭제도 보증하지 않는다.

다음 최소 단계는 회사에서 허용한 자료 읽기·보관 범위를 등록에 반영하고, 제공자·계정·전송 정책과 native 격리 실행 조건을 별도 확인하는 것이다. 현재 준비 자료를 실제 모델 호출에 자동 승격하지 않는다.
