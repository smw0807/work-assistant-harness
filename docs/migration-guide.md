# 회사 환경 이전용 오프라인 점검

`migration-check`는 하네스를 실행할 장비의 정적 준비 상태를 확인한다. 회사 저장소 경로를 입력받지 않으며 회사 코드·로그인 파일·인증값·기존 승인 DB를 읽지 않는다. 바이너리 실행, 로그인 확인/refresh, 네트워크 연결과 실제 모델 호출도 하지 않는다.

통과 결과는 회사 자료 처리 승인이나 실행 권한이 아니다. 보고서의 `liveReady`, `executionAllowed`, `approvalCreated`는 항상 `false`다. 실제 격리 동작, 로그인 유효성, 공급자 연결과 회사 자료 정책은 이 점검의 검증 범위 밖이다.

## 1. 실행 환경 준비

현재 실제 relay가 지원하는 호스트는 **macOS ARM64**다. Linux, Windows와 Intel Mac의 실제 호출 지원을 이 점검으로 추가하지 않는다. 지원하지 않는 호스트에서는 차단 결과를 확인하고 환경별 구현·격리 검증을 별도로 계획한다.

진단 입력도 기존 POSIX 절대 경로 형식을 유지한다. Windows 드라이브 형식의 경로는 입력 단계에서 거부되며, Windows에서의 명령 실행을 검증한 것은 아니다. 합성 호스트 관찰을 통한 미지원 OS 판정과 실제 다른 OS에서의 실행 검증을 구분한다.

하네스의 런타임 요구사항은 [package.json](../package.json)의 Node `>=26.12.1 <27`, pnpm `12.18.0`이다. 승인된 하네스 소스와 lockfile, 해당 런타임·의존성을 회사의 소프트웨어 반입 절차로 먼저 준비한다. 패키지 설치는 네트워크를 사용할 수 있는 별도 준비 작업이며, 점검 명령은 설치·다운로드·업그레이드를 수행하지 않는다. 의존성이 없으면 승인된 내부 배포나 패키지 저장소 절차로 준비한 뒤 점검한다.

점검에서 pnpm 버전은 실행기가 제공한 `npm_config_user_agent` 메타데이터로만 관찰한다. 이 값은 실제 pnpm 실행 파일의 신원을 증명하지 않으며 보고서에도 그 한계를 표시한다. Node의 현재 버전 검사와 구분한다. 메타데이터가 없으면 해당 검사는 `not_run`이고 전체 결과는 `blocked`다. OS·CPU·Node·pnpm의 기본 조건이 충족되지 않으면 바이너리·저장 경로의 후속 검사는 실행하지 않는다.

실제 relay의 고정 바이너리는 **macOS ARM64 native Codex 0.154.0**이고 기준 SHA-256은 다음과 같다.

```text
4f85982624b3898c8991cb80c0981b2aa71070e3537046c9a95950318a95afcc
```

회사의 반입 절차로 준비한 해당 바이너리를 사용한다. 바이너리는 현재 사용자 또는 root 소유의 단일 일반 파일이어야 하고, 실행 비트가 있으며 그룹·다른 사용자 쓰기 권한이 없어야 한다. 점검은 파일 크기·Mach-O ARM64 헤더·고정 hash를 확인하고 `/usr/bin/sandbox-exec`의 파일 메타데이터를 확인한다. Codex의 `--version`이나 `sandbox-exec`를 실행하지 않으므로 파일 확인이 실제 격리 동작을 증명하지는 않는다. 다른 버전의 바이너리에 맞춰 기준 hash를 바꾸는 방식으로 통과시키지 않는다.

개인 환경의 인증·캐시·DB·승인·보고서를 회사 환경으로 복사하지 않는다. 회사에서 사용할 OS 계정과 비공개 보관 위치를 별도로 정한다. 이 운영상 분리는 담당자가 준비하는 조건이며, 점검기가 계정이나 인증 상태를 자동으로 분리·검증하는 기능은 아니다.

## 2. 진단 설정 준비

[설정 템플릿](../config/migration-check.example.json)을 하네스와 대상 저장소 밖의 비공개 디렉터리에 `migration-check.json`이라는 이름으로 복사한다. 아래 절대 경로는 새로 사용할 위치로 바꾼다. 준비 명령은 선택한 새 디렉터리·설정 사본만 생성한다.

```sh
umask 077 &&
mkdir -m 700 /absolute/path/to/private-migration &&
mkdir -m 700 /absolute/path/to/private-runtime &&
cp config/migration-check.example.json /absolute/path/to/private-migration/migration-check.json &&
chmod 600 /absolute/path/to/private-migration/migration-check.json
```

기존 디렉터리를 재귀적으로 권한 변경하거나 기존 파일을 덮어쓰지 않는다. `&&`는 앞 단계가 실패하면 복사·권한 변경을 진행하지 않게 한다. 상위 디렉터리가 이미 있는 새 절대 경로를 선택한다. 예시 경로 그대로는 동작하지 않는다.

설정 사본에서 `relay.codexPath`와 `runtimeDirectory`를 준비한 절대 경로로 바꾼다. 진단은 `enabled: false`만 허용하며 설정을 활성화하거나 변경하지 않는다. `runtimeDirectory`는 현재 OS 사용자가 소유한 기존 `0700` 디렉터리여야 한다. 설정 파일은 `0600`, 설정의 보관 디렉터리는 `0700`으로 준비한다. 설정 파일 이름은 `migration-check.json` 또는 `migration-check.example.json`만 허용한다. 상위 디렉터리까지 심볼릭 링크가 없는 정규화된 경로를 사용하고, Codex 파일 이름은 `codex`로 둔다. 경로 구성 요소는 영문·숫자·공백·밑줄·마침표·하이픈으로 제한되며 상대 경로나 glob은 받지 않는다.

회사 저장소 경로, 질문, 계정 ID, 토큰, 인증 파일 경로, 임의 명령이나 네트워크 주소는 이 설정에 추가하지 않는다. 알 수 없는 필드와 알려진 인증 경로는 거부한다. 읽는 내용은 사용자가 명시한 진단 설정과 native 파일로 제한하므로 다른 파일을 진단 설정이나 바이너리 이름으로 위장해 지정하지 않는다. 저장 디렉터리는 하네스 소스·바이너리·진단 설정과 겹치지 않게 선택한다.

템플릿은 기존 relay v3 설정을 감싼 진단 입력이다. 기존 relay-v2, 개인 수집 v2와 실행 예산 v1을 변경하지 않는다. v3의 실행 120초·공유 정리 5초·총 125초·8192프레임, 응답 4MiB·개별 frame 64KiB·최종 16KiB를 유지한다. 수집의 원본/전체 view 64KiB·개별 발췌 32KiB·근거 64KiB·입력 128KiB·8파일/16범위/범위당 200줄도 유지한다. 이 진단 입력을 승인이나 실제 호출 설정으로 자동 전환하지 않는다.

## 3. 점검 실행과 결과 보관

하네스 저장소에서 실행한다.

```sh
pnpm harness migration-check --config /absolute/path/to/private-migration/migration-check.json
```

`pnpm harness`는 기존 스크립트대로 먼저 `tsc`를 실행하여 하네스의 `dist`를 빌드한다. 그 뒤 실행되는 진단은 지정한 설정·고정 바이너리를 제한적으로 읽고 필요한 경로 메타데이터만 검사한다. 런타임 디렉터리의 내용을 열거하거나 DB를 열고, 쓰기 시험 파일을 만들거나 기존 권한을 수정하지 않는다.

보고서를 파일로 보관하려면 소유한 비공개 디렉터리의 새 파일로 stdout을 저장한다. 다음 예시의 `--silent`는 pnpm의 스크립트 안내 출력을 제거한다. `set -C`는 기존 보고서 덮어쓰기를 막는다. 파일 보관은 호출한 셸의 동작이며 진단기에는 파일 출력 옵션이 없다.

```sh
umask 077
set -C
pnpm --silent harness migration-check --config /absolute/path/to/private-migration/migration-check.json \
  > /absolute/path/to/private-migration/report.json
```

보고서는 원시 파일 내용·설정 전문·절대 경로·인증값·환경변수 전문 대신 정해진 검사 상태와 이유, 계약/예산/수집 hash를 제공한다. 허용되지 않은 설정이나 경로의 원시 오류 메시지를 보고서로 복제하지 않는다. 진단 설정과 export 보고서는 Git에 넣지 않는다.

## 4. 결과 해석과 다음 단계

전체 `status`는 `passed` 또는 `blocked`다. 종료 코드 `0`은 정적 검사 통과이고, `1`은 차단 결과 또는 잘못된 입력이다. 잘못된 인자·설정 등은 보고서 생성 전에 고정 오류 코드로 거부될 수 있으므로 stdout 파일이 생겼다는 사실만으로 성공 처리하지 않는다. 검사별 `passed`는 구현된 정적 조건 통과, `failed`는 조건 불충족, `not_run`은 미실시를 뜻한다. 인증·모델·회사 자료 접근 등 진단 범위 밖 항목은 정상적으로도 `not_run`을 유지한다. 보고서의 검사별 이유를 확인하고 수치나 계약을 임의로 바꿔 우회하지 않는다. 누락된 환경을 준비한 뒤 새 진단을 수행한다.

쓰기 권한 비트와 소유자 검사는 파일시스템 ACL·용량·쓰기 성공의 증명이 아니다. 파일 메타데이터와 hash 검사는 이후 변경에 대한 영구 보증도 아니다. 실제 호출 시의 원본·승인·바이너리 재검증과 격리 검증은 계속 필요하다.

정적 준비가 끝나면 회사 기기에서 합성 자료를 이용한 로컬 검증 범위를 정한다. 회사 코드의 실제 읽기나 외부 AI 전송은 회사가 허용한 계정·자료 범위·보관 조건을 확인한 별도 계획으로 준비한다. 현재 진단은 회사 승인을 확인하거나 회사 저장소를 등록하지 않으며 실제 모델 호출도 승인하지 않는다. 개인 시험 저장소에서 추가 호출하는 것은 회사 이전의 필수 단계가 아니다.

구현·검증 결과는 [단계 4-C-14 결과](stage-4c14-result.md), 회사 자료의 권한과 보관 조건은 [보안과 승인](security-and-approval.md#7-회사-자료와-비밀정보)을 따른다.
