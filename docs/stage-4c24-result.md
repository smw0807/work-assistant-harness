## 단일 복구

승인한 제안 hash, 정책·새 등록·원본 관찰 목록과 controller/helper의 hash를 고정했다. 실행 직전에 기준 commit, 선택 경로, 현재 파일의 SHA-256·canonical Git blob SHA-1, 요청 객체 부재, index 검색 일치와 최종 guard를 다시 확인했다. 만료된 보고서나 등록 본문은 읽지 않았다.

별도 로컬 helper는 원본 크기·hash와 no-symlink/owner/identity를 확인하고, 같은 fanout의 새 임시 파일을 독점 생성해 기록·fsync한 뒤 final 경로에 독점 link했다. 자신의 임시 파일을 정리하고 최종 nlink=1, 압축 바이트·제한된 해제 결과와 객체 hash를 확인했다. 기존 final을 덮어쓰거나 삭제하는 경로는 없다. 오류로 link 이후 상태가 불확정이면 final을 보존하며 자동 재시도하지 않는다.

실제 결과는 새 blob1개·압축9,794B, 기존 fanout 사용, 임시 파일 정리와 자식 종료 확인이다. 선택 원본/Git 메타데이터13개는 전후 일치했고 제품 소스·HEAD·index는 변경하지 않았다. 회사 Git 명령·원격 접속·실제 인증·native·모델 호출·제품 설치/검사/빌드는 수행하지 않았다.

Node permission 모드의 범위 제한 write와 전체 write 허용 모두 합성 probe에서 fsync를 `ERR_ACCESS_DENIED`로 거부했다. fsync를 생략하지 않고, hash로 고정한 별도 신뢰 controller를 승인된 명령으로 실행했다. 경로·원본 검사와 30초/250ms 종료·old-space128MiB 제한을 적용했지만 이를 회사 준비 worker와 같은 파일 쓰기 격리로 설명하지 않는다. 기존 준비 worker의 권한·profile/hash·한도는 그대로다. 경로 전후 관찰은 원자적 파일시스템 snapshot을 보장하지 않는다.
